## 1. 阶段目标

到阶段 06 为止，我们的助手有了一堆**能力**（工具、MCP），但它对世界的了解**只来自模型的训练数据**。这会撞上三堵墙：

- **知识截止**：模型不知道上周发生了什么，也不知道你昨天写的那份文档；
- **私有数据**：公司的规章制度、你自己的笔记，模型从没见过；
- **幻觉**：遇到不知道的事，它会**一本正经地编**。

RAG（Retrieval-Augmented Generation，检索增强生成）就是解决这三件事的标准答案。它的思路朴素得惊人：

> **别指望模型记住一切。让它开卷考试——先去资料里找，再看着资料回答。**

学完这一阶段，你会：

- 说清 RAG 五个环节各自在解决什么问题：**切块 → 嵌入 → 入库 → 检索 → 生成**；
- 理解**切块**为什么必须做，以及 `chunk_size` / `overlap` 的权衡；
- 理解**嵌入**的本质：把"语义相近"变成"向量距离近"；
- 知道**距离度量必须和嵌入模型匹配**（BGE 用余弦，不是 L2）；
- 明白**向量库**到底做了什么（它不只是"存向量的数组"）；
- 建立起本阶段最重要的一条工程纪律：**调 RAG，先调检索**；
- 在前端把"检索到了什么"和"拼给模型的 prompt 长什么样"**摊开来看**。

> **为什么嵌入模型要放本地跑？**
> 因为 DeepSeek 不提供 embedding 接口——这是很多人的第一个意外。而且嵌入是"高频低价值"的调用：一次入库要算几十上百次。放本地既省钱又快，还完全离线。本项目用 **FastEmbed**（ONNX 实现），**不依赖 torch**，装完约 100MB。

> **关于模型来源**：我们写的是 `BAAI/bge-small-zh-v1.5`（这是模型在社区里的名字），但 FastEmbed 实际下载的是它自己转换好的 ONNX 版本（仓库 `Qdrant/bge-small-zh-v1.5`）。这正是 FastEmbed 的价值——**它替你把 PyTorch 模型转成了 ONNX**，所以你不必装 torch。缓存位置在 `%LOCALAPPDATA%\Temp\fastembed_cache`。

如果下载失败，按下面的顺序排查（这三种情况都很常见，且报错各不相同）：

| 报错 | 原因 | 处理 |
|---|---|---|
| 卡很久后超时 / 连接被重置 | 访问不了 HuggingFace | 设镜像后重启服务：`export HF_ENDPOINT=https://hf-mirror.com`（Windows PowerShell 用 `$env:HF_ENDPOINT="https://hf-mirror.com"`） |
| `SSL: CERTIFICATE_VERIFY_FAILED` | **未必是证书问题**。两种常见根因：① 域名被 hosts 劫持到本地（见下方技巧）；② 有代理在做 TLS 中间人，Python 的 CA 列表不认它的证书 | 先查解析；确认是劫持就换镜像。是代理则加 `NO_PROXY='*'` 或解决证书信任 |
| 下载到一半失败，之后报 `NO_SUCHFILE` | 缓存里的临时文件（`.incomplete`）没下完，快照目录不完整 | 删掉 `fastembed_cache/models--Qdrant--bge-small-zh-v1.5` 重来 |

> **一个排查技巧**：怀疑域名被劫持时，直接看解析结果最有效——
> ```python
> import socket; print(socket.gethostbyname("huggingface.co"))
> ```
> 正常应返回公网 IP。如果返回 `127.0.0.1`，说明 hosts 文件或 DNS 把它指向了本地，**这时候任何重试都不会成功**，换镜像才是正解。

> **下载太慢怎么办？** 镜像带宽有限时（实测约 90 KB/s），90MB 的权重可能要十几分钟，中途断了还会留一堆 `.incomplete`。这时可以**绕开下载器，直接用 `curl` 断点续传**：
> ```bash
> SNAP="$LOCALAPPDATA/Temp/fastembed_cache/models--Qdrant--bge-small-zh-v1.5/snapshots/<快照id>"
> curl -L -C - --noproxy '*' \
>   -o "$SNAP/model_optimized.onnx" \
>   https://hf-mirror.com/Qdrant/bge-small-zh-v1.5/resolve/main/model_optimized.onnx
> ```
> **关键一步是校验**：`hf` 缓存里的文件名就是内容的 sha256，`sha256sum` 对得上才算真的下完了——只看文件大小不够。这一招在"网络时好时坏"的环境里比反复重试靠谱得多。

## 3. 核心概念

### 3.1 RAG 的五个环节

```
① 切块 chunking     长文档塞不进上下文 → 切成小块
② 嵌入 embedding    文本 → 向量（一串数字），语义相近则向量相近
③ 入库 indexing     向量存进向量库，并建索引以便快速查找
④ 检索 retrieval    问题的向量 → 库里找最相近的 top-k 块
⑤ 生成 generation   把检索到的块拼进 prompt → 模型"看着材料回答"
```

**①②③④ 完全不需要 LLM。** 只有第 ⑤ 步才调用模型。这个划分是本阶段最重要的一张地图，因为它决定了你调优时该往哪儿看：

> **回答不对，先别怪模型——先看检索捞回来的是什么。**

阶段 06 我们已经撞过一次这个真相：模型说"课程笔记里没有 MCP 的条目"，不是因为模型笨，而是因为**我们给它的资料里确实没有**。RAG 把这件事从"偶然"变成了"系统"：**模型的答案质量，上限由检索结果决定。**

### 3.2 切块：为什么必须切

最直接的理由是**上下文有长度上限**。但即使上下文无限长，也必须切，原因有三个：

1. **成本与延迟**：把整本手册塞进 prompt，每次提问都要按 token 付费，还慢；
2. **噪声稀释**：一篇 5000 字的文档里，只有 200 字跟问题相关。整篇塞进去，关键信息会被淹没在无关内容里，模型反而更容易漏看；
3. **检索的粒度**：检索的单位就是块。块太大，召回的是"一整章"，你没法精确定位；块太小，一句话被切碎，语义不完整。

所以 `chunk_size` 是个**权衡**，没有普适最优值：

| chunk_size | 后果 |
|---|---|
| 太大（如 2000 字） | 一块里混了多个主题，检索命中但噪声大，模型容易抓错重点 |
| 太小（如 50 字） | 句子被拦腰截断，一块里没有完整语义，检索质量崩掉 |
| 中文常见取值 | **300–500 字**（本项目用 400），大致对应一段完整论述 |

**`overlap`（重叠）解决的是"接缝问题"**。假设答案是"深圳今天 32 度"：

```
不重叠：  ...深圳今天的天气是 | 阵雨，气温 32 度...
              块A 结尾             块B 开头
          两块都答不全
```

让相邻块保留一段重叠（本项目 80 字），答案无论落在哪儿，总有一块是完整的。

> 本项目的切块策略是"由粗到细"：**先按空行切段落**（尊重作者给的语义边界），段落超长再按中文句末标点切句，最后才硬切。这是"优先相信人类写的结构"——比无脑按字数切效果好得多。

### 3.3 嵌入：把语义变成坐标

嵌入模型做的事，是给每段文本算出一串固定长度的数字（本项目是 **512 维**）。它的神奇之处在于：

```
"深圳今天很热"        → [0.12, -0.03, 0.88, ...]
"深圳气温 32 摄氏度"  → [0.11, -0.02, 0.85, ...]   ← 和上面很接近
"这份合同的违约金"    → [-0.42, 0.61, -0.15, ...]  ← 差很远
```

**意思相近的文本，向量也相近。** 于是"找相关内容"就变成了一个纯粹的数学问题：**找距离最近的向量**。这就是为什么检索不需要 LLM——它根本不需要"理解"，只需要算距离。

**一个必须知道的细节：`embed()` 和 `query_embed()` 不是一回事。**

BGE 这类检索模型在训练时，对"文档"和"查询"用了不同的前缀（查询要加一句"为这个句子生成表示以用于检索相关文章"）。混用会让检索质量明显下降，而且**不会报错**——只是结果悄悄变差，非常难发现。FastEmbed 帮你处理了这个细节：

```python
def embed_documents(texts: list[str]) -> list[list[float]]:
    """把「待检索的文档」变成向量。"""
    return [v.tolist() for v in get_embedder().embed(texts)]

def embed_query(text: str) -> list[float]:
    """把「问题」变成向量。注意用的是 query_embed 而不是 embed。"""
    return next(iter(get_embedder().query_embed([text]))).tolist()
```

### 3.4 距离度量必须和模型匹配

算相似度有好几种方式（L2 欧氏距离、内积、余弦相似度），**用哪个不是随便选的，要跟模型的训练方式一致**。

BGE 系列是按**余弦相似度**训练的。而 ChromaDB 默认用 L2。这就是为什么创建集合时必须显式声明：

```python
return _client.get_or_create_collection(
    name=COLLECTION_NAME,
    metadata={"hnsw:space": "cosine"},   # ← 不写这行，排序结果会不一样
)
```

余弦相似度的取值范围是 `[-1, 1]`，越大越像。而 ChromaDB 返回的是**距离**（`distance = 1 - 相似度`），所以代码里做了换算，让"分数越大越相关"更符合直觉：

```python
"score": round(1.0 - float(dist), 4),
```

实测下来，中文短文本的余弦相似度大致落在这个区间，可以直接当"相关度仪表"用：

| 分数 | 含义 |
|---|---|
| ≥ 0.60 | 高度相关，基本就是答案所在 |
| 0.45 – 0.60 | 沾边，可能是相关背景 |
| < 0.45 | 基本是噪声，**该考虑加文档或改切块参数了** |

### 3.5 向量库到底做了什么

你可能会想：向量不就是数组吗，我自己写个循环算距离不行吗？

行，但那叫**暴力检索**（brute force）：N 个块就要算 N 次距离。几千个块还能忍，到了百万级就彻底不可用了。

向量库的价值在于**近似最近邻索引**（ANN，ChromaDB 用的是 HNSW——分层可导航小世界图）。它牺牲一点点召回率，换来从"线性扫描"到"对数级查找"的提速。所以：

- **小数据量**（本项目几百块）用不用向量库差别不大——但用它，你学到的接口能直接迁移到生产；
- **大数据量**必须有索引，这是向量库存在的根本理由。

此外向量库还顺手解决了持久化、元数据过滤（`where={"title": ...}`）、增量增删等问题——这些自己写会很烦。

### 3.6 第五步：把检索结果"拼"进 prompt

这一步是 RAG 里的 **A**（Augmented，增强）。做法直白到没有任何魔法：

```python
def build_prompt(question: str, hits: list[dict]) -> str:
    blocks = [
        f"[资料 {i}] 来源《{h['title']}》第 {h['index']} 段\n{h['text']}"
        for i, h in enumerate(hits, 1)
    ]
    return "参考资料：\n\n" + "\n\n".join(blocks) + f"\n\n用户问题：{question}"
```

生成的 prompt 长这样：

```
参考资料：

[资料 1] 来源《07-RAG基础》第 42 段
CHUNK_SIZE = 400       # 中文按字符切：400 字约等于一段完整论述
CHUNK_OVERLAP = 80     # 80 字重叠，防止答案落在块的接缝上
...

[资料 2] 来源《07-RAG基础》第 25 段
...

用户问题：RAG 的切块大小和重叠是怎么设置的？
```

两个设计要点：

1. **给每块标注来源**（`《标题》第 N 段`）——这样模型能"引用出处"，你也能核对它有没有乱说；
2. **system prompt 要下死命令**：

```python
RAG_SYSTEM_PROMPT = (
    "你是一个严谨的研究助手。请**只依据**下面提供的「参考资料」回答用户问题。\n"
    "规则：\n"
    "1. 资料里有的，就依据资料回答，并注明是第几段资料；\n"
    "2. 资料里没有的，直接说「资料里没有相关内容」，不要凭记忆补充；\n"
    "3. 不要编造资料里不存在的细节。"
)
```

**第 2 条是本阶段的灵魂。** 不写这条，模型遇到资料里没有的问题时会"热心地"用记忆补上——你就又回到幻觉了。这跟阶段 06 那条经验是同一件事：**模型的诚实程度，取决于你有没有明确允许它说"我不知道"。**

### 3.7 RAG 的三种失败模式

上线后你一定会遇到"答得不对"。请按这个顺序排查，**不要一上来就改 prompt**：

| 现象 | 真正的原因 | 该改哪里 |
|---|---|---|
| 答"资料里没有"，但资料里明明有 | **检索没捞到**（切块太碎 / 用词差异大 / top_k 太小） | 调 `chunk_size`、加大 `top_k`、改进查询 |
| 捞到了但答非所问 | **检索捞错了**（噪声块挤掉了正确块） | 换嵌入模型、加元数据过滤、上重排（阶段 08） |
| 捞对了但模型不用 | **生成没听话**（system prompt 不够硬，或块太多被稀释） | 改 system prompt、减少 `top_k` |

> **中栏的「检索」为什么必须单独存在？** 因为它把"检索问题"和"生成问题"分开了。如果只有一个"问答"按钮，你永远分不清是检索坏了还是模型坏了——而这恰恰是 RAG 调试中最浪费时间的一件事。

### 4.2 后端 · 嵌入：`rag.py`

```python
EMBED_MODEL = "BAAI/bge-small-zh-v1.5"   # 中文小模型，约 100MB，512 维

_embedder: TextEmbedding | None = None

def get_embedder() -> TextEmbedding:
    """懒加载嵌入模型（首次调用会下载权重到本地缓存）。"""
    global _embedder
    if _embedder is None:
        try:
            _embedder = TextEmbedding(model_name=EMBED_MODEL)
        except Exception as e:
            raise RuntimeError(
                f"加载嵌入模型 {EMBED_MODEL} 失败：{e}。"
                "首次使用需从 HuggingFace 下载权重；若网络不通，"
                "可先设置环境变量 HF_ENDPOINT=https://hf-mirror.com 再重启服务。"
            ) from e
    return _embedder
```

**懒加载 + 明确的错误提示**是两个工程细节：懒加载让服务启动不必等模型；明确的错误提示让你不用去猜"为什么第一次调用卡了 30 秒然后失败"。

**还有一个必须放在文件最顶上的顺序问题**：

```python
from dotenv import load_dotenv
load_dotenv()                          # ← 必须在下面这行之前执行

import chromadb                        # noqa: E402
from fastembed import TextEmbedding    # noqa: E402
```

`huggingface_hub` 是在 **import 的那一刻**读取 `HF_ENDPOINT` 的，之后再改环境变量就晚了。所以 `.env` 必须先加载——这样你只要在 `backend/.env` 里写一行 `HF_ENDPOINT=...`，不用去改系统环境变量。因为 import 被夹在中间，这几行会触发 linter 的"import 不在文件顶部"告警，用 `# noqa: E402` 明确表示**这是有意为之**。

`PersistentClient` 会**落盘**——重启服务后知识库还在。想重来一遍就删掉 `backend/.chroma/` 目录（它已在 `.gitignore` 里）。

入库时用「标题 + 序号」做 id，并在重复导入同一标题前先清旧块，让操作**幂等**：

```python
def add_document(title: str, text: str) -> dict:
    chunks = split_text(text)
    delete_document(title)                      # 幂等：重复导入 = 覆盖
    ids = [f"{title}#{i}" for i in range(len(chunks))]
    collection.add(
        ids=ids,
        documents=chunks,
        metadatas=[{"title": title, "index": i} for i in range(len(chunks))],
        embeddings=embed_documents(chunks),
    )
    return {"title": title, "chunks": len(chunks), "chars": len(text), "preview": chunks}
```

`preview` 返回**切块后的真实文本**——这是给前端展示"文档被切成了什么样"的，也是本阶段最好玩的一块。

```python
def ask(client, question, top_k=3, model=None) -> dict:
    """完整 RAG：检索 → 拼 prompt → 生成。"""
    hits = search(question, top_k=top_k)
    prompt = build_prompt(question, hits)
    answer = client.chat(
        [{"role": "system", "content": RAG_SYSTEM_PROMPT},
         {"role": "user", "content": prompt}],
        model=model, temperature=0.2,
    )
    return {"answer": answer, "hits": hits, "prompt": prompt, "model": ...}
```

> 阶段 08 会给这个函数**追加**三个带默认值的参数（`mode` / `rerank` / `candidates`），
> 把「检索」这一步换成可配置的管道。默认值仍是纯向量，所以这里写的调用方式**不会失效**。

**返回值里带上 `hits` 和 `prompt` 是有意为之。** 阶段 06 我们把 JSON-RPC 报文摊给了用户看，这一阶段我们把"模型到底看到了什么"摊开——**可解释性是同一个思路的延续**。

### 4.6 前端 · `useRag.ts` + `RagConsole.vue`

`useRag.ts` 与阶段 06 的 `useMcp.ts` 结构相似，但**三条链路各自独立**（入库 / 检索 / 问答），并用一个 `busy` 字段精确标记"当前哪一步在跑"：

```ts
const busy = ref<'' | 'status' | 'ingest' | 'seed' | 'search' | 'ask' | 'reset'>('')
```

这样界面上只有被点击的那个按钮转圈，而不是全局灰掉——细节，但体验差别很大。

`RagConsole.vue` 是三栏控制台：

- **左 · 知识库**：状态卡（文档数 / 块数 / 嵌入模型 / 切块参数）、导入示例文档、文档列表（可删）、手动粘贴入库，以及**切块结果预览**（逐块列出 `#0 #1 #2...` 的真实文本）。
- **中 · 检索（不调 LLM）**：输入问题 → top-k 结果，每条带**相似度进度条**与三档配色（青绿 ≥0.6 / 琥珀 ≥0.45 / 灰 其余）。这块就是"调 RAG 先调检索"的工作台。
- **右 · RAG 问答**：提问 → 回答 + **引用资料列表**（`[1] 07-RAG基础 · 第 42 段 0.8144`）+ **可展开的完整 prompt**。

**右栏那个"拼给模型的 prompt"是本阶段的产品价值**：用户第一次能亲眼看到"检索"是怎么变成"增强"的——原来模型看到的不是我的问题，而是"一堆资料 + 我的问题"。

**一个必须亲眼看见的失败**——「MCP 有哪三条铁律？」：

```
TOP  1  0.4974  《06-MCP协议开发》#27    ← 只讲"第三条铁律"
TOP  2  0.4914  《06-MCP协议开发》#101
TOP  3  0.4867  《07-RAG基础》#22
...
TOP 25  0.4343  《06-MCP协议开发》#29    ← 三条铁律齐全的那一块

标准答案块（`06#29`，正文写着「至此三条铁律齐了：**① stdout 是协议通道；② 通知不回应；③ server 不认识 LLM。**」）在 **333 块里排第 25 名**——`top_k` 就算开到 8 也捞不到。

为什么？看这块的内容：它的**前 80 字是上一块的尾巴**（重叠带来的），主体讲的是"模型能修复 vs 不能修复"的对比和 `mcpkit` 命名坑，**"三条铁律"只占最后一句**。块的向量被占多数篇幅的其他内容主导了——**答案只占块的一小部分，检索就找不到它**。这是 RAG 最典型、也最容易被忽略的失败。

归到前面那张表里，它属于**没捞到**。可用的修法：混合检索（关键词能精确命中"三条铁律"）、重排、或把块切得更小——**正是阶段 08 要做的三件事**。

**另一个失败**——阶段总表：

`DESIGN.md` 里的「阶段映射总表」被切成了 `#5` / `#6` / `#7` / `#8` 四块，其中 `#5` 的结尾甚至只剩表头、没有表行：

```
DESIGN#5   ... ## 三、阶段映射总表 | 阶段 | 内容 | 形态 | |---|---|---|          ← 只有表头
DESIGN#6   ... | 00 | 环境与工具准备 | ... | 08 | RAG 进阶（混合检索/重排） |    ← 第 00–08 行
DESIGN#7   ... | 06 | ... | 15 | Deep Research | 主线 |                        ← 第 06–18 行
DESIGN#8   ... | 17 | 多模态·语音 | ... | 18 | Computer Use | ...             ← 第 17–18 行 + 下一节
```

于是问「第 09 到第 15 阶段是主线还是能力插件？」，TOP 1 落在**含第 17/18 行**的 `#8`（0.6682），而真正含第 09–15 行的 `#7` 排在第二（0.5970）。**两块本是同一张表的两截，模型却得猜哪一截才算数。**

> 表格是**结构化数据**，而"按字符数切"完全不懂结构。这提醒你：**切块策略要跟着语料形态走**——纯散文和满是表格的文档，不该用同一套参数。

**③ 完整 RAG 问答**

同样语料，`POST /api/rag/ask`（`top_k=3`），实测三次：

| 问题 | 检索最高分 | 耗时 | 结果 |
|---|---|---|---|
| RAG 的切块大小和重叠是怎么设置的？ | 0.8144 | 5.27 s | ✅ 完整正确 |
| MCP 有哪三条铁律？ | 0.4974 | 5.36 s | ⚠️ 只答出 1 条，**但如实说明了** |

拼给模型的 prompt 长度 951–1041 字符（3 块资料 + 问题），端到端 4–6 秒——**比阶段 03 的纯对话只慢一点点**，因为嵌入和检索都在本地，几乎不占时间。

第一次答得干净利落，而且**逐条标了出处**：

```
切块大小：资料 2 第 25 段显示为 400 字，注释说明"中文按字符切：400 字约等于一段完整论述"。
重叠大小：资料 2 第 25 段显示 CHUNK_OVERLAP = 80，即 80 字重叠……
切块策略：资料 2 第 25 段和资料 3 第 12 段都说明是"由粗到细"……
```

第二次最能说明问题。检索只捞到第三条铁律，模型的回答是：

```
根据提供的资料，**只能确认第三条铁律**，另外两条没有出现。
……
至于 MCP 的第一条铁律和第二条铁律，资料里没有相关内容，因此无法依据这些资料列出完整的三条铁律。
```

**这正是 `RAG_SYSTEM_PROMPT` 第 2 条想要的效果**：它没有凭记忆把另外两条编出来，而是老实说"资料里没有"。**RAG 的价值不只是答得更准，更是让"不知道"变得可见**——换成没有 system prompt 约束的裸模型，这里大概率会流畅地背出三条铁律，而你根本不知道其中两条不在资料里。

第三次暴露了另一个问题。问"今天北京的天气"，库里最高分只有 0.4283（噪声档），但模型还是从 05 号教程的**实测记录块**里拎出了 `get_weather(北京) → 26℃`：

```
根据资料 1，调用 get_weather(北京) 得到的实测结果是 26℃……
不过，资料里没有提到北京更具体的天气状况……也没有说明这是否就是"今天"的天气。
```

它**没有撒谎**（资料里确实写着 26℃），但把一个"教程里的模拟数据"当成"天气信息"端给了你。**低分块一旦被拼进 prompt，模型不会主动拒绝使用它**——它只会尽力从里面找出点东西。

> 这条经验可以直接变成一行代码：**设一个分数下限**，低于它的块干脆不拼进 prompt。本项目故意没有加，就是为了让你看见不加会怎样。练习里可以把它补上。

## 6. 小结

- RAG 的思路是**开卷考试**：不指望模型记住一切，让它先去资料里找，再看着资料回答。
- 五个环节 **切块 → 嵌入 → 入库 → 检索 → 生成**，**前四个都不需要 LLM**——这张地图决定了你调优时该往哪儿看。
- **切块是权衡**：太大则噪声稀释，太小则语义破碎；中文常见 300–500 字，`overlap` 用来解决"答案落在接缝上"。
- **嵌入**把"语义相近"变成"向量距离近"，于是检索变成了纯数学问题。
- **`embed()` ≠ `query_embed()`**，**距离度量必须匹配模型**（BGE 用 cosine，不是 ChromaDB 默认的 L2）——这两点错了都不会报错，只会悄悄变差。
- 向量库的核心价值是 **ANN 索引**（HNSW），把线性扫描变成对数级查找。
- 第五步的"增强"就是把检索结果**拼进 prompt**，并且 system prompt 必须**明确允许模型说"资料里没有"**。
- 本阶段最重要的纪律：**调 RAG，先调检索。** 中栏那个"不调 LLM 的检索"就是为此存在的。
- 三种失败模式（没捞到 / 捞错了 / 捞对了没用）指向三个不同的修法，**别一上来就改 prompt**。

## 7. 练习与验收

**改造题**：给 RAG 加一个「**元数据过滤**」能力——检索时可以指定只在某一份文档里找。

提示：

1. 后端 `search()` 增加 `title: str | None = None` 参数，传给 ChromaDB 的 `where`：`where={"title": title} if title else None`；
2. `RagSearchRequest` / `RagAskRequest` 增加 `title` 字段；
3. 前端中栏加一个下拉框，选项来自已入库的文档标题（多一个"全部"）；
4. 验证：把 `top_k` 设为 3，先在"全部"里搜一个词，再限定到某一份文档里搜同一个词，观察**结果与分数如何变化**。

**验收标准**

1. 限定文档后，检索结果的 `title` 全部是所选文档；
2. 同一个查询，限定范围后**相似度分数不变**（因为向量没变），但**排序可能变化**——能解释为什么；
3. 当所选文档里确实没有相关内容时，返回空列表，且前端给出明确提示（而不是静默无响应）；
4. 问答时限定文档，回答里的引用编号只出现该文档的来源。

**思考题（不写代码）**
