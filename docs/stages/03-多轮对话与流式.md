## 1. 阶段目标

- 理解**为什么从这一阶段起必须有后端**：密钥、上下文拼装、协议转换三件事都不该由浏览器承担。
- 掌握多轮对话的本质：**多轮不是模型的记忆，而是你每次把整段历史重新发一遍**。
- 掌握 SSE 流式：后端逐块推送 delta，前端用原生 `fetch + ReadableStream` 边收边渲染。
- 学会用 `AbortController` 打断一次正在进行的生成。
- 从本阶段开始，前端不再出现任何 API Key。

## 3. 核心概念

### 3.1 为什么必须有后端

阶段 01–02 让前端直连模型，是为了让你看清「请求体到底长什么样」。但从现在起必须收回来，原因是四个：

1. **密钥**：前端的 Key 等于公开的 Key，谁都能从浏览器里抄走。
2. **上下文拼装**：多轮对话需要维护历史，还要裁剪、注入 system，这是服务端职责。
3. **协议转换**：模型吐出的是 SDK 的 chunk 对象，前端需要的是能直接渲染的文本流——中间要有人翻译（本阶段翻译成 SSE）。
4. **未来扩展**：RAG 检索、工具调用、多智能体都要在服务端编排，前端不该知道。

一句话：**前端只负责渲染，其余都归后端。**

### 3.2 多轮对话 = messages 数组的累积与回放

HTTP 是无状态的，模型本身也不"记住"你。所谓多轮，不过是每轮请求时把之前所有消息**再发一遍**：

```
第 1 轮  POST [system, user₁]                       → assistant₁
第 2 轮  POST [system, user₁, assistant₁, user₂]     → assistant₂
第 3 轮  POST [system, user₁, assistant₁, user₂, assistant₂, user₃] → assistant₃
```

由此直接推出三个结论：

- **上下文会越来越长** → token 消耗与延迟随轮数线性增长（界面右下角实时显示"上下文 N 条"就是让你看见这件事）。
- **历史在谁手里，谁就能改答案**：删掉中间一轮，模型就"忘了"那件事。这也是后续做摘要压缩、RAG 注入的入口。
- 本课程阶段 03–06 把历史放在**前端**（`messages` 数组）；阶段 07 起才会搬进 SQLite 做服务端持久化。两种做法都是"每轮全量回放"，区别只是谁来保存这份数组。

### 3.3 一次性返回 vs 流式

| | 一次性（`stream=false`） | 流式（`stream=true`） |
|---|---|---|
| 返回 | 一个完整 JSON | 一连串 chunk，每个带一点 `delta` |
| 首字延迟 | 等全部生成完（可能 10s+） | 几百毫秒就出第一个字 |
| 体感 | 转圈圈 | 像有人在打字 |
| 适用 | 批处理、程序化调用 | 交互式产品（几乎全部） |

流式不改变最终内容，只改变**到达方式**。chunk 里有用的字段只有一个：

```json
{"choices":[{"delta":{"content":"你"}}]}
```

### 3.4 SSE：一个二十行就能说清的协议

SSE（Server-Sent Events）的报文格式极其简单——每帧就是：

```
data: <内容>\n\n
```

以空行（`\n\n`）分帧，内容里不能有裸换行，所以大家都塞 JSON。我们自定义了三种帧：

```jsonc
data: {"delta": "增量文本"}                    // 来一点，追加一点
data: {"done": true, "model": "deepseek-flash"} // 正常收尾
data: {"error": "模型调用失败：..."}             // 流中途出错（此时状态码已发出，只能靠帧报错）
```

两个常见疑问：

- **为什么不用 `EventSource`？** 它只支持 GET，而我们要 POST 一整段对话历史。
- **为什么不用 WebSocket？** 我们只需要服务端→客户端的单向推送，SSE 更轻，且自带断线重连与文本分帧。

### 3.5 前端怎么读这条流

不用任何库，四步：

1. `fetch(..., { signal })` 拿到 `response.body`（一个 `ReadableStream`）；
2. `body.getReader()` + `TextDecoder('utf-8')` 按块解码，**必须传 `{ stream: true }`**，否则跨块的中文会被截成乱码；
3. 把解码结果追加到 `buffer`，按 `\n\n` 切成若干帧；
4. **最后一帧可能只收到一半**，要留在 buffer 里等下一块，绝不能丢。

## 4. 动手实现

### 4.1 后端 · 自封装 client：`llm.py`

只依赖 OpenAI SDK 的协议层，换厂商 = 换 `base_url` + `api_key`：

```python
class LLMClient:
    def __init__(self, api_key=None, base_url=None, model=None):
        self.model = model or DEFAULT_MODEL
        key = api_key or os.getenv("DEEPSEEK_API_KEY", "").strip()
        if not key:
            raise LLMNotConfiguredError("未检测到 DEEPSEEK_API_KEY：请复制 .env.example 为 .env")
        self._client = OpenAI(api_key=key, base_url=base_url or DEFAULT_BASE_URL)

    def chat(self, messages, model=None, temperature=0.7) -> str:
        resp = self._client.chat.completions.create(
            model=model or self.model, messages=messages, temperature=temperature, stream=False,
        )
        return resp.choices[0].message.content or ""

    def stream(self, messages, model=None, temperature=0.7):
        resp = self._client.chat.completions.create(..., stream=True)
        for chunk in resp:
            delta = chunk.choices[0].delta.content if chunk.choices else None
            if delta:
                yield delta          # 生成器：来一块吐一块
```

要点：`stream()` 是**生成器**，调用它不会立刻发起请求，只有在 `for` 循环里逐次 `next()` 时才推进——这正是流式能"边生成边推送"的关键。

### 4.2 后端 · 契约：`schemas.py`

```python
class Message(BaseModel):
    role: Literal["system", "user", "assistant"]
    content: str = Field(min_length=1)

class ChatRequest(BaseModel):
    messages: list[Message] = Field(min_length=1)
    model: str | None = None
    temperature: float = 0.7
```

Pydantic 在这里做了三件事：校验结构、自动生成 OpenAPI 文档（`/docs` 可直接调试）、把类型错误挡在业务代码之外。

### 4.3 后端 · 两个路由：`main.py`

非流式：

```python
@app.post("/api/chat", response_model=ChatResponse)
def chat(req: ChatRequest) -> ChatResponse:
    client = get_client()
    content = client.chat(to_dicts(req.messages), model=req.model, temperature=req.temperature)
    return ChatResponse(content=content, model=req.model or client.model)
```

流式（本阶段核心）：

```python
def sse(payload: dict) -> str:
    return f"data: {json.dumps(payload, ensure_ascii=False)}\n\n"

@app.post("/api/chat/stream")
def chat_stream(req: ChatRequest) -> StreamingResponse:
    client = get_client()

    def event_gen():
        try:
            for delta in client.stream(to_dicts(req.messages), model=req.model):
                yield sse({"delta": delta})
            yield sse({"done": True, "model": req.model or client.model})
        except Exception as e:
            yield sse({"error": f"模型调用失败：{e}"})   # 流已开始，只能用帧报错

    return StreamingResponse(event_gen(), media_type="text/event-stream", headers=sse_headers())
```

三个容易踩的坑，都写在代码里了：

- `ensure_ascii=False`：否则中文全变成 `\u4f60`，前端虽能解析，但人眼调试时是天书。
- `X-Accel-Buffering: no`：有 Nginx 等反代时，不加这行流式会被缓冲成"最后一次吐出"。
- **流式一旦开始，HTTP 状态码就发出去了**，之后的错误只能走帧内容，别再指望 `HTTPException`。

### 4.4 前端 · `useChatStream.ts`

```ts
const resp = await fetch(`${apiBase}/chat/stream`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ messages: context.value, temperature: 0.7 }),
  signal: controller.signal,
})

const reader = resp.body.getReader()
const decoder = new TextDecoder('utf-8')
let buffer = ''
for (;;) {
  const { value, done } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })   // 关键：stream: true
  const frames = buffer.split('\n\n')
  buffer = frames.pop() ?? ''                         // 半帧留在 buffer
  for (const frame of frames) {
    const line = frame.split('\n').find((l) => l.startsWith('data:'))
    if (!line) continue
    const payload = JSON.parse(line.slice(5).trim())
    if (typeof payload.delta === 'string') target.content += payload.delta
    else if (payload.error) error.value = payload.error
    else if (payload.done) return
  }
}
```

组合式对外只暴露 `system / messages / loading / error / turnCount / send / stop / reset`：`messages` 用 `readonly()` 包一层，组件只能读，改对话必须走 `send / reset`——这就是 `props down / events up` 在 composable 层面的体现。

`stop()` 就是 `controller.abort()`：`fetch` 会抛 `AbortError`，`catch` 里判断 `err.name !== 'AbortError'` 才当作真错误，所以**已生成的内容会被保留**。

### 4.5 前端 · `StreamChat.vue`

- **消息列表**：用户靠右（Signal 琥珀调）、助手靠左；每条带 `YOU / ASSISTANT` 等宽小标。
- **签名元素**：助手消息流式期间尾部挂闪烁 caret，生成结束收成实心青绿句点——这是本课程贯穿始终的视觉锚。
- **system 人设**：单独一行输入，每轮都会作为 `messages[0]` 带上（阶段 02 练习题的答案在这里落地）。
- **打断**：生成中「发送」置灰、出现「停止生成」。
- **元信息**：右下角 `上下文 N 条 · POST /api/chat/stream`，让你随时看见上下文在变长。

## 6. 小结

- 多轮对话没有魔法：**历史数组 + 每轮全量回放**。上下文长度就是成本，界面上那个"N 条"就是账单。
- 流式也没有魔法：模型分块生成 → 后端包成 SSE 帧 → 前端按 `\n\n` 切帧累加。变的是到达方式，不是内容。
- 后端在这里承担了三件前端做不到/不该做的事：保管密钥、拼装上下文、翻译协议。
- 工程细节决定体验：`TextDecoder({ stream: true })` 防中文乱码、半帧留 buffer 防丢字、`X-Accel-Buffering: no` 防反代缓冲、`AbortController` 给用户对生成的控制权。
- 设计系统延续：Ink/Panel 面板、Signal 琥珀标注用户输入、Data 青绿流式光标。

## 7. 练习与验收

**改造题**：给控制台加一个**「流式 / 一次性」切换开关**。开时用 `/api/chat/stream`（逐字渲染），关时走 `/api/chat`（转圈等待后整段出现），并把两者的**首字出现时间**显示在消息头。

提示：
1. `useChatStream` 里新增 `sendSync(text)`：`fetch('/api/chat')` → `await resp.json()` → 直接写 `target.content`；
2. 组件里加一个 `el-switch`，`onSubmit` 按开关分派；
3. 计时：`const t0 = performance.now()` 发请求前打点，收到第一个 `delta` 或拿到 JSON 时 `performance.now() - t0`。

**验收标准**

1. 同一句话两种模式都能拿到完整、一致的回复内容；
2. 一次性模式的首字时间明显大于流式模式（通常差一个数量级）；
3. 切换开关不影响多轮历史，两种模式共用同一份 `messages`；
4. 流式模式仍可中途停止，一次性模式在等待期间按钮保持禁用。
