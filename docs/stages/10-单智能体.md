## 1. 阶段目标

先看一个已经能跑、但读起来很别扭的循环。阶段 05 的 `run_tool_loop` 是这样的：

```
while 还有步数:
    resp = 模型(messages, tools)
    if resp 没有 tool_calls:   return resp.content      # 结束
    for call in resp.tool_calls:
        messages.append(执行结果)                        # 继续
```

它已经能调工具了。但它缺三样东西，**这三样正是本阶段的内容**：

| 缺什么 | 后果 |
|---|---|
| **显式的 Thought** | 模型要么给答案、要么给 `tool_calls`。**推理过程完全不可见，也不进入上下文**——下一步只能盯着"上一步的原始结果"做决定，而不是"上一步的结论" |
| **统一的工具面** | 只有 4 个玩具工具。MCP（06）、RAG（07/08）、GraphRAG（09）各管各的，模型没法自己挑 |
| **停止条件的纪律** | 只有一个 `max_steps`。真实的 agent 还必须处理**死循环**、**上下文膨胀**、**预算耗尽后怎么收口** |

本阶段要做的三件事：

```
① 显式推理   每轮先写 Thought（想什么）→ 再 Action（调什么）→ 再读 Observation（看到了什么）
② 统一工具面 local 4 个 + RAG + GraphRAG + MCP，收进一张清单，按组开关
③ 停止纪律   步数预算 / 死循环硬停 / 观测截断 / 被迫收口
```

学完你应该能回答：

- ReAct 比阶段 05 的 tool loop 多做了什么？为什么这一点能减少幻觉？
- 工具的 `description` 为什么说"就是 prompt"？写含糊会怎样？
- 什么叫"工具面重叠"？为什么它会让 API 直接报错？
- 步数用完了该怎么办？为什么"返回一个错误"是坏选择？
- 流式输出时，你怎么知道这一段文字是"它在想"还是"它在回答"？
- 阶段 09 的 SSE 要"后台线程 + 队列"，本阶段的 SSE 为什么不需要？

## 3. 核心概念

### 3.1 ReAct 是什么

ReAct = **Reason + Act**（Yao et al., 2022）。它的贡献可以用一句话说完：

> **让模型在每一步行动之前，先把推理写出来，并让这段推理留在上下文里。**

循环长这样：

```
Thought      我现在知道什么、还缺什么、下一步为什么选这个工具
Action       调哪个工具、传什么参数
Observation  工具返回了什么
...（循环）
Finish       信息够了，给出答案
```

三个环节的角色分工很清楚：

- **Thought** 是"把账算清楚"——它是**自然语言**，不是结构化字段。这一点很关键：
  模型在写"还缺什么"的时候，实际上是在给自己列 TODO。
- **Action** 是唯一会碰外部世界的环节。**它是唯一可能失败的地方。**
- **Observation** 是"世界给的反馈"。它不由我们编造，所以**它有可能打脸**。

### 3.2 为什么显式 Thought 能减少幻觉

这是本阶段最该想透的一点。

阶段 03 那种"直接回答"的链路里，模型的每一句话**都没有纠错机会**——
它说错了，也没人反驳，只能一路错到底。

ReAct 不一样：

```
Thought:  我记得 RAG 的切块大小是 400
Action:   search_course_docs({"query": "切块大小"})
Observation: {"CHUNK_SIZE = 400", ...}      ← 对上了，继续
```

或者：

```
Thought:  我记得切块大小是 512
Action:   search_course_docs({"query": "切块大小"})
Observation: {"CHUNK_SIZE = 400", ...}      ← 打脸了，必须改口
```

**每一次断言都有机会被 Observation 打脸。** 这就是它减少幻觉的机制，
没有更玄的东西。所以有个推论：**如果你给的工具都查不到，ReAct 反而可能更糟**——
模型会把"没查到"当成"我说得对"的默许。这也是为什么下一节要讲
"工具返回值是给模型读的 prompt"。

### 3.3 工具的 `description` 就是 prompt

对 agent 来说，`description` **不是文档，是给模型看的指令**。
它决定了模型会不会、以及什么时候选这个工具。

对比一下同一件事的两种写法：

```python
# ❌ 含糊：模型不知道"什么时候该用我"
"query_knowledge_graph": "查询知识图谱。"

# ✅ 具体：写清了适用场景，还顺手做了排除
"query_knowledge_graph":
    "在课程知识图谱里查**关系**（谁依赖谁、谁属于谁、谁包含谁）。"
    "适合「X 属于哪个阶段」「X 用了什么」这类问题——这类问题的答案往往"
    "不在任何一段原文里，只有图上才有。问的是事实而非关系时用 search_course_docs。"
```

第二种写法的最后一句"问的是事实而非关系时用 search_course_docs"，
**是在两个工具之间划边界**。工具一多，边界比功能更重要——
模型选错工具，往往不是因为不知道工具能干什么，而是因为不知道**该在什么时候用它**。

### 3.4 工具面：统一注册表 + 分组开关

到阶段 10，我们手上一共有四批能力：

```
local   4 个玩具工具（阶段 05）
rag     search_course_docs      （阶段 07/08）
graph   query_knowledge_graph   （阶段 09）
mcp     MCP Server 提供的工具   （阶段 06）
```

把它们收进同一张清单之后，做了一件在前几个阶段做不到的事：
**让用户亲手勾掉几组，再问同一个问题。**

勾掉 RAG，问一个课程事实问题——模型要么说"我不知道"，
要么**硬编**。这个对照比任何"工具面很重要"的说教都有说服力。

### 3.5 ⚠️ 工具面重叠：一个真实存在的问题

写这个阶段的时候撞上一个坑，值得单独讲。

阶段 06 的 MCP Server 是怎么实现的？看 `mcpkit/server.py`：

```python
from tools import TOOLS, all_notes, execute_tool

def _list_tools(_params: dict) -> dict:
    return {"tools": [ ... for t in TOOLS.values() ]}     # ← 就是阶段 05 那 4 个
```

**它把阶段 05 的工具又暴露了一遍。** 于是当用户把「本地工具」和「MCP Server」
**同时勾上**时，`build_schemas()` 会吐出两份 `calculator`：

```
['calculator', 'search_notes', 'get_weather', 'get_current_time',
 'search_course_docs', 'query_knowledge_graph',
 'calculator', 'search_notes', 'get_weather', 'get_current_time']   ← 重复！
```

而 **OpenAI 协议不允许重名工具**。实测把这个 10 条的清单发给 DeepSeek：

```
❌ BadRequestError
   Error code: 400 - {'error': {'message': 'Tool names must be unique. ...',
                                'type': 'invalid_request_error'}}
```

**整个 agent 起不来**——不是选错工具，是请求根本发不出去。

真实的 MCP host（Claude Desktop、Claude Code）用**命名空间**隔离：
工具名会变成 `mcp__<server>__<tool>`。本项目用更朴素的做法：

> **同名去重，按组优先级保留第一个：`local > rag > graph > mcp`。**

为什么本地优先？因为它**是进程内的一次函数调用**（实测 **0.1ms**），
而 MCP 版本要经过 JSON-RPC 序列化 → 管道 → 子进程 → 再原路返回。
同样一件事，本地快一个数量级。名字相同时把便宜的那个留给模型，是划算的。

被挤掉的名字不会消失——接口会把重叠情况照实列出来，前端显示给用户：

```
calculator         同时来自 ['local', 'mcp'] → 实际生效 local
get_current_time   同时来自 ['local', 'mcp'] → 实际生效 local
get_weather        同时来自 ['local', 'mcp'] → 实际生效 local
search_notes       同时来自 ['local', 'mcp'] → 实际生效 local
```

**让用户看见"重叠"，比悄悄藏起来有价值**——它正好说明：**工具面是需要设计的。**

### 3.6 停止条件的纪律

阶段 05 只有一个 `max_steps`。真实 agent 要处理三件事：

**(1) 死循环。** 模型会犯轴——同一个工具、**完全相同的参数**反复调。
结果一定和上次一样，继续跑只是烧钱。所以：

```python
if used[sig] > max_repeat:      # max_repeat 默认 2，即第 3 次拒绝
    拒绝执行，并把原因写进 Observation
```

注意签名要把参数**排序**后再序列化，否则 `{"a":1,"b":2}` 和 `{"b":2,"a":1}`
会被当成两次不同的调用——模型换个字段顺序就能绕过护栏。

**(2) 上下文膨胀。** Observation 会被塞进 `messages`，而且它通常比 Thought **长得多**。
一次返回 3 段 1000 字的原文，几步下来上下文就爆了。两道防线：

```python
_HIT_TEXT_LIMIT = 400        # 工具内部就截断：每条命中最多留 400 字
observation_limit = 1200     # 循环里兜底：单条 Observation 最多 1200 字符
```

**真正的解法是第一道**——在工具内部就限制返回量。
第二道只是保险丝，因为它截断的是已经拼好的 JSON，会破坏结构。

**(3) 预算耗尽后怎么收口。** 步数用完时，两个选择：

```
❌ 返回一个"未收敛"的错误     → 用户白等了 30 秒，什么都没拿到
✅ 禁用工具，逼它用现有信息作答 → 用户至少拿到一个有依据的答案
```

第二种做法只是在 `messages` 末尾追加一句：

```
已经到达步数上限。**请不要再调用任何工具**，直接根据上面已有的信息给出最终答案。
如果信息不足以回答，就如实说明缺什么，不要编造。
```

**并且这次调用不传 `tools` 参数**——模型没有任何可调的东西，只能输出文本。
这比"返回 None"有用得多。

### 3.7 流式下的一个固有歧义

这一节是本阶段最"工程"、也最容易被忽略的一点。

我们要"看着 agent 想"，所以 Thought 必须流式吐出来。但流式有一个绕不开的问题：

> **你没法提前知道这一轮吐出的文本是 Thought，还是最终答案。**

两者的开头长得一模一样。唯一的分界线是**这一轮结束时有没有 `tool_calls`**——
而流式的定义就是"在结束之前就得吐出来"。

所以只能**先流出来、再定性**：

```
收到 delta      → 先落进一个中性的 live 缓冲区
收到 action     → 刚才那段确认是 Thought，落进思考区
收到 finish     → 刚才那段其实就是答案，丢掉缓冲，改用 finish.answer
```

后端为此把事件名从 `thought_delta` 改成了中性的 **`delta`**——
叫 `thought_delta` 是在替前端做它做不了的判断。

前端相应地只有**一个** live 区域，而不是"思考区 + 答案区各写一份"。
好处是**永远不会重复渲染**：同一段文字只会出现在一个地方，定性之后"落位"。

这不是设计缺陷，是流式 agent 的常态。**"先输出、后标注"是它的基本手法。**

### 3.8 agent 的工具要在"准"和"快"之间重新取平衡

阶段 08 得出过一个结论：**混合检索必须开重排**，因为它能把第 25 名捞到第 1 名。

到了 agent 场景，这个结论**不再是无条件的**：

```python
def _run_rag_search(query: str, top_k: int = 3) -> dict:
    # ⚠️ 故意关掉重排（rerank=False）
    found = rag.hybrid_search(query, top_k=top_k, mode="hybrid", rerank=False, candidates=10)
```

因为重排一次要 600ms 左右，而 agent 可能在同一个问题里调好几次检索——
**单次请求的延迟会被放大成总时长**。用户盯着时间线，等的是"下一步什么时候来"，
不是"这一步的排序够不够精"。

教训：**在 agent 里，工具是"被调用方"，它的性能指标从"单次质量"变成了"单位时间产出"。**
阶段 08 那个结论没错，只是它的前提（一次检索、一次回答）在 agent 里不成立了。

## 4. 动手实现

### 4.1 后端 · 流式 tool_calls 的拼装（整条链路上最容易写错的一段）

`llm.py` 原有三个方法，各差一半：

| 方法 | 能流式？ | 能读 tool_calls？ |
|---|---|---|
| `stream()`（阶段 03） | ✅ | ❌ 只给纯文本 |
| `chat_message()`（阶段 05） | ❌ 必须等整轮跑完 | ✅ |
| **`stream_message()`（本阶段）** | ✅ | ✅ |

ReAct 两样都要，所以只能自己拼分片。**这里有个必须知道的细节**：

```python
# ⚠️ tool_calls 的分片不是"每个 chunk 一个完整调用"，
# 而是按 index 分组的**字段级碎片**：
#   第一个 chunk 可能只给了 id 和 name，
#   arguments 要跨好几个 chunk 才拼得完整（模型是一个 token 一个 token 吐 JSON 的）。
# 所以必须按 index 建槽位、逐字段**累加**，而不是覆盖。

slots: dict[int, dict[str, str]] = {}
for chunk in resp:
    delta = chunk.choices[0].delta
    if delta.content:
        content += delta.content
        yield {"delta": delta.content}          # 文本增量，直接吐
    for frag in getattr(delta, "tool_calls", None) or []:
        slot = slots.setdefault(frag.index, {"id": "", "name": "", "arguments": ""})
        if frag.id:
            slot["id"] = frag.id                # id 只在第一片出现，直接赋值
        fn = getattr(frag, "function", None)
        if fn is not None:
            if fn.name:
                slot["name"] += fn.name         # ⚠️ 累加
            if fn.arguments:
                slot["arguments"] += fn.arguments  # ⚠️ 累加
```

实测拼装结果：

```
增量 8 片段 → '我先算一下这个表达式的值。'
tool_calls  → calculator + {"expression": "(23+17)*3"}
```

`index` 是唯一可靠的槽位键。用 `id` 当键会挂——因为**第一个分片之后 `id` 就不再出现了**。

### 4.2 后端 · 把"组 → 工具"收敛成单一真相来源

`react.py` 里最容易写出 bug 的地方，不是循环，是**工具的装配**。

最初 `build_schemas()` 和 `tool_catalog()` 各自维护了一份"哪个工具属于哪一组"的映射。
两份一旦不同步，就会出现"schema 里有这个工具、执行器却不认"的幽灵 bug。
所以先把它收敛成一处：

```python
def _group_tools(groups=None) -> tuple[dict[str, list[dict]], dict[str, str | None]]:
    """**唯一的"组 → 工具"真相来源。**"""
```

顺便解决一个性能问题——**MCP 只在真的勾了它时才去碰**：

```python
# ⚠️ get_host().describe() 会**拉起一个子进程**，
# 而 build_schemas 在每轮 run_react 开头、甚至拼错误信息时都会调。
# 不勾 MCP 却每次都 fork 一个进程，是白白付的启动成本。
if GROUP_MCP in wanted:
    ...
```

### 4.3 后端 · 同名工具去重

```python
def build_schemas(groups=DEFAULT_GROUPS) -> list[dict]:
    wanted = set(groups)
    by_group, _errors = _group_tools(wanted)

    out, seen = [], set()
    for group in ALL_GROUPS:        # 顺序即优先级 local > rag > graph > mcp
        if group not in wanted:
            continue
        for tool in by_group[group]:
            if tool["name"] in seen:
                continue
            seen.add(tool["name"])
            out.append(_to_schema(tool))
    return out
```

实测：全勾四组 → 原始 10 条，去重后 **6 条**，无重名。

不做这一步的后果不是"模型选错"，而是 API 直接拒绝（见 §3.5 的 400 报错）。

### 4.4 后端 · ⚠️ 执行器的认领顺序必须和 schema 一致

这是写这个阶段时抓到的**第二个真 bug**，而且它很隐蔽。

原来的执行器分发是这样的：

```python
# ❌ 问题代码
if name in TOOLS:
    if GROUP_LOCAL not in groups:
        return None, f"工具 {name} 当前未启用（没勾选「本地工具」）"
    return execute_tool(name, raw_arguments)
```

看起来没问题。但考虑"**只勾 MCP、不勾本地**"这个组合：

1. `build_schemas` 去重后，`calculator` 来自 MCP 那一组 → schema 是对的；
2. 模型调 `calculator`；
3. 执行器走到 `if name in TOOLS:` → **成立**（`TOOLS` 是阶段 05 的静态表，和勾选无关）；
4. 然后发现本地组没启用 → **拒绝执行**。

**MCP 那一支永远走不到。** 模型会一直收到"工具未启用"，
而它明明勾着 MCP——用户看到的现象是"勾了 MCP 但工具全废"。

修法是让**认领条件**带上组：

```python
# ✅ 判断顺序要和 build_schemas 的去重优先级严格一致
if name in TOOLS and GROUP_LOCAL in groups:
    return execute_tool(name, raw_arguments)

# 不满足就往下走，落到 MCP 那一支
if mcp_exec is not None:
    result, error = mcp_exec(name, raw_arguments)
```

修完实测：

```
只勾 MCP：
  schema = ['calculator', 'search_notes', 'get_weather', 'get_current_time']
  calculator({"expression": "(23+17)*3"}) → ✅ {"expression": "(23+17)*3", "value": 120}
```

**这个 bug 的教训比修法重要**：schema 和执行器是同一份事实的两面，
它们**必须用同一个顺序做同一套判断**。任何"我在这边过滤一下、那边再判断一下"的写法，
都是在给自己埋雷。

### 4.5 后端 · ReAct 主循环（写成生成器）

```python
def run_react(client, question, *, model=None, max_steps=6, temperature=0.2,
              groups=DEFAULT_GROUPS, observation_limit=1200, max_repeat=2) -> Iterable[dict]:
    groups = list(groups) or list(DEFAULT_GROUPS)
    schemas = build_schemas(groups)
    executor = make_executor(groups)

    yield {"type": "start", "tools": [s["function"]["name"] for s in schemas], ...}

    messages = [
        {"role": "system", "content": REACT_SYSTEM},
        {"role": "user", "content": question},
    ]

    for step in range(1, max_steps + 1):
        thought, message = "", None
        for event in client.stream_message(messages, model=model,
                                           temperature=temperature, tools=schemas):
            if "delta" in event:
                thought += event["delta"]
                yield {"type": "delta", "step": step, "text": event["delta"]}
            else:
                message = event["message"]

        calls = message.get("tool_calls") or []
        if not calls:                       # 没有 Action = 模型认为信息够了
            yield {"type": "finish", "reason": "answered", "answer": message["content"], ...}
            return

        messages.append(message)            # assistant 这轮的话（含 tool_calls）必须原样写回
        for call in calls:
            ...执行、追加 role="tool" 消息、yield action / observation
```

**写成生成器是刻意的**：ReAct 的演示价值全在"看着它想"，
路由层把它直接接进 SSE，每一帧就是时间线上的一行。

### 4.6 后端 · 死循环硬停

```python
for call in calls:
    name, raw = call["function"]["name"], call["function"]["arguments"]
    args = _safe_args(raw)
    sig = _signature(name, args)
    used[sig] = used.get(sig, 0) + 1
    repeats = used[sig] - 1

    # ⚠️ 同一个 (工具, 参数) 第 3 次出现就**拒绝执行**。
    # 继续跑只是烧钱——结果一定和上两次一样。
    if used[sig] > max_repeat:
        content = (f"⛔ 拒绝执行：{name} 用**完全相同的参数**已经被调用过 {repeats} 次，"
                   "结果不会有任何变化。请换参数、换工具，或直接用已有信息回答。")
        loop_hit = True
    else:
        result, error = executor(name, raw)
        content, ok = _render(result, error)
        # 还没到硬停但已经是重复：明确告诉它"这次和上次一样"
        if repeats > 0:
            content += f"\n\n⚠️ 注意：{name} 用完全相同的参数你已经调用过 {repeats} 次了，本次结果与上次相同。"
```

签名要把参数排序：

```python
def _signature(name: str, args: Any) -> str:
    return f"{name}::{json.dumps(args, sort_keys=True, ensure_ascii=False)}"
```

### 4.7 后端 · 上下文预算

```python
# 用字符数当预算的代理指标。真实项目会换成 tokenizer，
# 但**"Observation 比 Thought 长得多"这个结论与度量单位无关**。
context_chars = sum(len(m.get("content") or "") for m in messages)
yield {"type": "step_end", "step": step, "contextChars": context_chars}
```

### 4.8 后端 · 被迫收口也要流式

步数耗尽 / 死循环之后要禁用工具逼它收口。**这里很容易顺手写成 `client.chat()`**
（反正就一句话）。但那样用户会看到：

```
时间线卡住 3 秒 → 答案整段冒出来        ← 和前面几步逐字吐出的观感完全对不上
```

所以抽了一个 `_forced_finish()`，**仍然走 `stream_message()`**：

```python
def _forced_finish(client, messages, model, temperature, reason, step, steps, total_ms, t_start):
    """...⭐ **这里仍然流式。** 一旦决定流式，就得全程流式——
    一致性的价值大于省那几行代码。

    产出的 delta 用的是**同一个 step 号**，所以前端那条"收到 finish 就丢掉
    当前 step 的缓冲区"的规则照样适用，不需要为收口路径写特例。"""
    messages.append({"role": "user", "content": FORCE_FINISH})
    for event in client.stream_message(messages, model=model, temperature=temperature):
        # 不传 tools → 模型没有任何可调的东西
        ...
```

### 4.9 后端 · 路由：⭐ 和阶段 09 对照着看

阶段 09 的 SSE 长这样：

```python
def event_gen():
    def worker():                       # 后台线程
        graph.build(..., on_progress=lambda *a: frames.put(...))
        frames.put(None)                # 哨兵
    yield sse({"phase": "start"})
    thread = threading.Thread(target=worker, daemon=True)
    thread.start()
    while True:
        item = frames.get()             # 队列
        if item is None:
            break
        yield sse(item)
```

**本阶段的 SSE 长这样：**

```python
def event_gen() -> Iterator[str]:
    try:
        for event in react.run_react(client, req.question, ...):
            yield sse(event)            # 就这。
    except Exception as e:
        yield sse({"type": "error", "message": f"智能体运行失败：{e}"})
```

没有线程、没有队列、没有哨兵。

差别不在技巧，在**控制权**：

| | 阶段 09 | 阶段 10 |
|---|---|---|
| 被包的东西 | `graph.build()` —— 一个**阻塞的黑盒** | `run_react()` —— **我们自己写的生成器** |
| 能否从中间掏进度 | ❌ 只能等它跑完 | ✅ 每一步都在我们的控制流里 |
| 代价 | 线程 + 队列 + 哨兵 | 0 |

**能自己拆开的流程，就别用线程去绕。**
线程带来的每一个队列和哨兵，都是将来某次"卡住不动"的伏笔。

顺带说一句：生成器里抛异常只会**断流**，前端什么都看不到。
所以整个循环包在 `try` 里，把异常转成一帧 `error` 发出去。

### 4.10 前端 · 单一 live 区域

对应 §3.7 的歧义，`useAgent.ts` 里只有**一个**缓冲区：

```ts
/**
 * ⭐ **单一 live 区域。**
 *
 * 流式下有个绕不开的歧义：**你没法提前知道这一轮吐出的文本是 Thought 还是最终答案**，
 * 唯一的分界线是这一步结束时有没有 `action`。
 *
 * 所以这里只有**一个** `live` 缓冲区，而不是"Thought 区 + 答案区各写一份"：
 *   - 收到 `action`   → 把 `live` 落成这一轮的 Thought，然后清空；
 *   - 收到 `finish`   → 清空 `live`，答案由 `finish.answer` 接管。
 *
 * 好处是**永远不会重复渲染**——同一段文字只会出现在一个地方，
 * 定性之后"落位"到它该去的卡片里。
 */
const live = ref('')
```

事件处理就是三个分支：

```ts
case 'delta':   live.value += p.text ?? ''; break

case 'action': {
  const s = ensureStep(p.step ?? 0)
  if (live.value) { s.thought = live.value; live.value = '' }   // 定性为 Thought
  s.actions.push({ ... })
  break
}

case 'finish':
  live.value = ''                    // 这段 live 其实是答案 —— 丢掉，改用权威版本
  answer.value = p.answer ?? ''
  break
```

界面上，live 卡片用的是一个 `?` 标签而不是 `Thought`：

```html
<div class="node pending">
  <span class="node-tag">?</span>
  <p class="node-body">{{ live }}<span class="caret"></span></p>
</div>
<p class="live-note">
  流式下<b>没法提前知道</b>这段文本是 Thought 还是最终答案——唯一的分界线是这一步结束时
  <b>有没有 <code>action</code></b>。所以只能先流出来、再定性。
</p>
```

**把不确定性画出来**，比假装它不存在好——用户看到 `?` 就知道"它还没定性"，
而不是看到一个写着 `Thought` 的标签、结果内容是答案。

### 4.12 前端 · ⚠️ 一个 flex 面板的陷阱

写样式时顺手给时间线面板加了一行：

```css
/* ❌ 看起来很"专业"，其实是 bug */
.timeline-panel { min-height: 0; }
```

`.agent-console` 是个 `overflow-y: auto` 的 flex 列，面板是它的 flex item。
**flex item 默认的 `min-height: auto`（= 内容高度）正是"不许被压扁"的保护**。
一旦改成 0，内容一多，面板就会被压到比内容矮，**卡片直接从边框里溢出去**。

修法是反过来钉死：

```css
.panel {
  ...
  /* ⚠️ 必须 flex-shrink: 0。这里显式钉死，让面板保持内容高度、由外层负责滚动。 */
  flex-shrink: 0;
}
```

这个坑值得记一笔，因为 `min-height: 0` 在**另一个位置**是完全正确的写法——
`App.vue` 里的 `.app-console { flex: 1 1 auto; min-height: 0; overflow: hidden; }`
就必须这么写，否则内层滚不动。
**同一个属性，在"滚动容器本身"和"被滚动的内容"上要求正好相反。**

### 5.4 实测记录：一条"病态指令"和模型的拒绝

想演示死循环护栏，于是给了模型一条明确要求重复的指令：

> 请反复用同一个参数调用 search_notes 查询「流式」，直到我说停。

模型的反应（`max_repeat=1`）：

```
💭 Thought: **Thought（想）**：用户要求我用完全相同的参数调用 `search_notes` 两次。
   但同参数重复调用同一个工具不会产生新信息，这违反了我的作业纪律
   （不重复调用、不为了多调而调）。所以我先调一次拿到结果，然后……
🔧 Action  search_notes({'query': '流式'})
✅ Observation  0.0ms
🏁 Finish(answered)
```

**它当场拒绝了，还引用了纪律条款。** 这带来一个比"演示成功"更有价值的结论：

> `REACT_SYSTEM` 里的纪律是**第一道防线**，硬停护栏是**兜底**。
> 护栏平时不响，不是因为它没用，而是因为第一道防线先拦住了。
> **别指望靠护栏去管住一个 prompt 写坏的 agent。**

所以前端的预设按钮标的是"**病态指令 · 看它会不会当场拒绝**"，
而不是"触发死循环"——**如实描述比强行造一个 demo 好**。

   # 结论: 重排是在**阶段 08「RAG 进阶」**引入。
```

比"返回未收敛错误"强的地方。

## 6. 小结

**本阶段新增的能力**

```
backend/react.py            715 行（新）  工具分组 / 统一注册表 / ReAct 循环 / 三道停止护栏
backend/llm.py              +79 行        stream_message()：流式拿完整 message（含 tool_calls 拼装）
backend/schemas.py         +126 行        工具目录 / 重叠 / 运行请求 / 结构化 trace
backend/main.py             +91 行        三条路由：tools / run / stream
frontend/useAgent.ts        511 行（新）  时间线状态机 + 单一 live 缓冲
frontend/AgentConsole.vue   737 行（新）  三色时间线 / 工具面勾选 / 预算旋钮 / 答案卡
frontend/AgentPage.vue        7 行（新）  页面包装
```

**四条最该带走的经验**

1. **ReAct 的全部价值在"推理外化"。**
   阶段 05 的循环也能调工具，但模型下一步面对的是"上一步的原始结果"；
   ReAct 让它面对"上一步的结论"。这个差别在跨工具依赖链上看得最清楚
   （§5.2 C：第二步的 Thought 里带着 `CHUNK_SIZE = 400`）。

2. **工具的 `description` 就是 prompt，工具之间的"边界"比"功能"更重要。**
   模型选错工具，多半不是不知道工具能干什么，而是不知道什么时候该用它。

3. **同一个事实只能有一个出处。**
   `build_schemas` 和 `make_executor` 必须用**同一个顺序**做**同一套判断**——
   本阶段为此踩了两个真 bug：工具重名（API 直接 400）、
   以及"只勾 MCP"时执行器抢先认领却拒绝执行（§4.3 / §4.4）。

4. **流式是有代价的，而且代价会以"语义歧义"的形式出现。**
   "先流出来、再定性"不是偷懒，是流式 agent 的固有约束。
   承认它、把它画进 UI（那个 `?` 标签），比假装它不存在好。

**和阶段 09 的一句话对照**

> 阶段 09 的流式要"后台线程 + 队列"，因为 `graph.build()` 是个阻塞的黑盒；
> 阶段 10 的流式只要 `for ... yield`，因为 `run_react()` 是我们自己写的生成器。
> **能自己拆开的流程，就别用线程去绕。**

## 7. 练习与验收

### 练习 A（必做）· 把 RAG 勾掉

打开 `/agent`，**取消勾选「课程检索（RAG）」**，然后问：

> 阶段 08 里重排用的是什么模型？

观察两件事：

1. 模型会不会去调 `query_knowledge_graph`？（大概率会，然后锚定失败）
2. 它最终是**如实说"没有这个信息"**，还是**凭记忆编一个**？

把它的最终答案和开着 RAG 时的答案并排贴出来。
**这个对照就是"工具面决定了模型能力的边界"最直接的证据。**

### 练习 B（必做）· 步数预算调成 1

把「步数预算」改成 **1**，问一个需要多步的问题（比如"多步依赖"预设）。

观察：

- 它在**只有一次工具机会**的情况下，会先调哪个工具？
- 被迫收口时，它给出的答案**有没有引用**？
- `reason` 显示的是"步数耗尽"——对照 §3.6 想一下：
  如果这里改成"返回错误"，用户的体验会差在哪？

### 练习 C（必做）· 观测上限调成 200

把「观测上限」改成 **200** 字符，问"多步依赖"预设的问题。

观察：

- 截断标记 `已截断 x.xk → 0.2k` 出现了几次？
- **它还能答对吗？** 如果答错了，看看是哪个关键信息被截掉了。

然后回答一个问题：**为什么 §3.6 说"真正的解法是在工具内部截断，而不是在循环里截断"？**

### 练习 D（必做）· 触发一次"工具面重叠"的坑

1. 只勾「本地工具」+「MCP Server」（**关掉** RAG 和 Graph），问"帮我算 (23+17)*3"；
2. 再**只勾**「MCP Server」，问同一个问题。

两次都能算对。然后打开浏览器 DevTools 的 Network 面板，
看两次请求的 **`tools` 参数长度**——第二次会更长吗？为什么？

> 提示：去看 §4.4。第一次是 local 认领，第二次是 MCP 认领。
> 如果你把 §4.4 那个 bug 改回去（`if name in TOOLS:` 不带组条件），
> 第二次就会直接失败。

### 练习 E（选做）· 给护栏加一条"预算护栏"

现在的三道护栏管的是**步数**、**重复**、**观测长度**。
真实项目还要管**钱**。

试着加第四个参数 `max_tokens`：

1. 在 `run_react` 的每步末尾累加 `len(messages)` 里所有内容的字符数（或接一个真的 tokenizer）；
2. 超过预算时，走和"步数耗尽"一样的 `_forced_finish`；
3. 在 `finish` 事件里加一个 `reason: 'budget'`，前端加一条 `REASON_TEXT`。

验收：`max_tokens` 调得很小时，能在第 2 步就被强制收口，且前端显示新的标签。

### 练习 F（选做）· 让 agent 记住跨轮的事

现在每次点「运行」都是**全新的对话**——`messages` 从零开始。
试着加一个"多轮模式"：

1. `useAgent.ts` 里保留上一次的 `messages`（或让后端维护一个会话）；
2. 新一轮的 `question` 追加到历史之后，而不是替换；
3. 观察：第二轮它会不会**复用**第一轮查到的结论（不再重复检索）？

> 这个练习是阶段 12「Agent Harness」的引子——
> 一旦 agent 开始有跨轮的状态，就牵出了"状态存哪、怎么裁剪、怎么恢复"一整套问题。
