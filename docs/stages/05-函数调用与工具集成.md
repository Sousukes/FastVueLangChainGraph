## 1. 阶段目标

- 纠正最普遍的一个误解：**模型不会执行任何代码**。它只产出"调用意图"，执行永远是我们的活。
- 用 Pydantic 参数模型**自动生成** JSON Schema，一份定义同时供模型阅读与运行时校验。
- 手写工具循环（tool loop）：模型 → `tool_calls` → 执行 → `role="tool"` 结果回喂 → 直到给出答案。
- 学会把"工具失败"变成模型能读懂的输入，让模型自纠或如实告知用户，而不是 500。
- 建立安全意识：**模型给的参数是不可信输入**，绝不能直接 `eval`。
- 在 UI 里把 trace 摊成时间线，让"模型为什么这么答"变得可解释。

## 3. 核心概念

### 3.1 模型不执行代码——它只会"申请"

这是本阶段唯一必须刻进脑子的事：

```
你给模型：工具说明书（name / description / parameters JSON Schema）
模型给你：{"name": "calculator", "arguments": "{\"expression\":\"(1234+876)*3/7\"}"}
```

模型从头到尾**没有运行过任何东西**。它只是根据"用户想算什么"和"有个叫 calculator 的工具"推断出"应该调用它、参数是这个"。真正算数的是我们自己的 Python 函数。所以：

- 工具能做什么、不能做什么，**完全由我们决定**（模型无法越权）。
- 危险操作（发邮件、删文件）在这里天然有一道闸门——你完全可以选择"不提供"或"要求确认"。

### 3.2 工具说明书：一份定义，两个用途

工具定义写两遍（一遍给模型、一遍给校验）是常见的坏味道。用 Pydantic 只写一遍：

```python
class CalculatorArgs(BaseModel):
    expression: str = Field(description="要计算的算术表达式，只支持数字与 + - * / // % ** 和括号")

# 给模型：JSON Schema
CalculatorArgs.model_json_schema()
# → {"properties": {"expression": {"type": "string", "description": "..."}},
#    "required": ["expression"], "type": "object"}
```

`Field(description=...)` 就是**写给模型看的文档**——写得越清楚，模型选错工具、给错参数的概率越低。`Literal["celsius","fahrenheit"]` 会自动变成 JSON Schema 的 `enum`，模型就只能在候选项里挑。

### 3.3 一次完整往复

```
① messages + tools 说明书  →  模型
② 模型回：tool_calls（可能一次多个，也可先不调用直接答）
③ 把模型这轮的话（含 tool_calls）原样 append 进 messages     ← 顺序不能反
④ 逐个执行工具，把结果以 role="tool" + tool_call_id 追加
⑤ 带着工具结果再问模型
⑥ 模型给出纯文本答案 → 循环结束
```

③④ 的顺序和 `tool_call_id` 配对是两个硬约束：

- 必须先写回 assistant 消息，再写 tool 结果，否则协议不成立；
- 每个 `role="tool"` 消息必须带 `tool_call_id` 指向它对应的那次调用——**一次并行调用多个工具时，模型靠 id 分辨哪个结果属于哪个请求**。

### 3.4 把"失败"做成模型能读懂的信息

工具失败有三类，处理方式一致：**转成文本回传，不抛异常**。

| 失败类型 | 例子 | 回传内容 |
|---|---|---|
| 参数不合法 | `{}` 缺 `expression` | `参数不符合 schema：expression: Field required` |
| 业务失败 | 查"火星"的天气 | `ValueError: 没有 火星 的天气数据，目前仅支持：北京、上海、深圳、杭州` |
| 工具不存在 | 模型幻觉出一个 `nope` | `未知工具 nope。可用工具：calculator, ...` |

为什么不能直接 500？因为**模型看得见 tool 消息**。把"没有火星的数据"告诉它，它会改成"抱歉，我只有北京/上海/深圳/杭州的数据"；把"你漏了参数"告诉它，它会补上参数再来一次。这与阶段 04 的自纠是同一个套路。

### 3.5 循环必须能停：`max_steps`

模型有可能陷入"一直调工具"（尤其当工具描述含糊、或工具总是返回错误时）。工程上必须有个硬上限：

```python
for step in range(1, max_steps + 1):
    ...
return {"answer": None, "exhausted": True}   # 到上限仍未收敛
```

`exhausted=True` 不是"程序出错"，而是一个**诊断信号**：说明工具描述需要改、或该把上限调高、或模型在某个错误上打转。

### 3.6 安全：模型给的参数是不可信输入

工具参数来自模型，而模型可能被用户诱导。所以：

```python
# 错误示范
eval(expression)

# 本课程做法：AST 白名单，只放行数字与算术运算
_ALLOWED_BINOPS = {ast.Add, ast.Sub, ast.Mult, ast.Div, ast.FloorDiv, ast.Mod, ast.Pow}
_ALLOWED_UNARY = {ast.UAdd, ast.USub}
```

实测把 `__import__('os').system('ls')` 塞进 `expression`，会在 AST 检查阶段被拦下（`不支持的表达式结构：Call`），函数体根本不会执行。**凡是"模型产出的字符串"进入执行路径，都要过这道关。**

## 4. 动手实现

### 4.1 后端 · 工具注册表：`tools.py`

```python
@dataclass(frozen=True)
class Tool:
    name: str
    description: str
    args_model: type[BaseModel]
    fn: Callable[..., Any]

TOOLS = {"calculator": Tool(...), "search_notes": Tool(...), "get_weather": Tool(...), "get_current_time": Tool(...)}

def tools_schema() -> list[dict]:
    return [{"type": "function",
             "function": {"name": t.name, "description": t.description,
                          "parameters": t.args_model.model_json_schema()}}
            for t in TOOLS.values()]
```

四个内置工具各有教学意图：

| 工具 | 演示什么 |
|---|---|
| `calculator` | 单参数 + **安全求值**（AST 白名单） |
| `search_notes` | 多参数（含 `limit` 上限 `ge=1, le=5`）+ 呼应后面的 RAG |
| `get_weather` | 枚举参数（`Literal` → JSON Schema `enum`）+ 业务错误（未知城市） |
| `get_current_time` | 真实 IO（时区）+ 呼应"时间不要自己算" |

执行入口统一为一个函数：

```python
def execute_tool(name: str, raw_arguments: str) -> tuple[Any, str | None]:
    tool = TOOLS.get(name)
    if tool is None:
        return None, f"未知工具 {name}。可用工具：{', '.join(TOOLS)}"
    try:
        raw = json.loads(raw_arguments or "{}")
    except json.JSONDecodeError as e:
        return None, f"arguments 不是合法 JSON：{e}"
    try:
        args = tool.args_model.model_validate(raw)      # 参数校验：非法参数不进入函数体
    except ValidationError as e:
        return None, f"参数不符合 schema：{hints}"
    try:
        return tool.fn(**args.model_dump()), None
    except Exception as e:
        return None, f"{type(e).__name__}: {e}"
```

### 4.2 后端 · 循环：`agent.py`

```python
for step in range(1, max_steps + 1):
    msg = client.chat_message(messages, model=model, temperature=0.2, tools=tools_schema())
    calls = getattr(msg, "tool_calls", None)
    if not calls:                                  # 模型直接回答 → 结束
        return {"answer": msg.content, "trace": trace, "steps": step, "exhausted": False}

    messages.append(message_to_dict(msg))          # ① 先写回 assistant（含 tool_calls）

    for call in calls:                             # ② 再逐个执行 + 写回 tool 消息
        result, error = execute_tool(call.function.name, call.function.arguments)
        trace.append({"step": step, "tool": ..., "arguments": ..., "result": ..., "error": ..., "ms": ...})
        messages.append({"role": "tool", "tool_call_id": call.id,
                         "content": json.dumps(result if error is None else {"error": error}, ensure_ascii=False)})
```

`temperature=0.2`：工具调用是"确定性任务"，低温能显著减少乱调。`trace` 里带上 `ms` 是为了让用户看见"哪个工具慢"。

### 4.3 后端 · client 扩展：`llm.py`

```python
def chat_message(self, messages, model=None, temperature=0.7, tools=None, tool_choice=None):
    resp = self._client.chat.completions.create(
        **self._payload(messages, model, temperature, None, tools, tool_choice), stream=False)
    return resp.choices[0].message        # 完整 message：content + tool_calls

def message_to_dict(msg) -> dict:
    out = {"role": "assistant", "content": msg.content or ""}
    if getattr(msg, "tool_calls", None):
        out["tool_calls"] = [{"id": c.id, "type": "function",
                              "function": {"name": c.function.name, "arguments": c.function.arguments}}
                             for c in msg.tool_calls]
    return out
```

`_payload` 增加两个可选键：`tools` 与 `tool_choice`（默认 `"auto"`）。

### 4.5 前端 · `useToolRunner.ts` + `ToolConsole.vue`

`useToolRunner` 干三件事：拉工具清单（`GET /api/tools`）、把 `parameters` 的 JSON Schema 摊平成可展示的参数行（`paramsOf`）、POST `/api/tools/run`。

`ToolConsole.vue` 是三栏控制台：

- **左 · 工具清单**：卡片展开显示参数（名称/类型/必填/描述）——这就是"模型看到的世界"。
- **中 · 提问**：5 个预设各对应一种调用形态（单工具 / 并行两工具 / 连续两轮 / 知识检索 / 工具会报错），一键填入。下面是最终回答。
- **右 · 调用时间线**：每个 `trace` 节点用竖线 + 圆点串起来，**成功节点青绿、失败节点琥珀**，展示 `arguments` / `result`（或 `error`）/ 耗时。

预设问题的设计意图（这就是本阶段的"考点"）：

| 预设 | 观察点 |
|---|---|
| 单工具 | 一次调用后直接回答 |
| 并行两工具 | 同一 `step` 两个 `tool_calls`，模型一次问两个 |
| 连续两轮 | `get_weather` → `calculator`，模型**拿到结果后决定再调一个**（问题带条件，用深圳 32℃ 保证条件成立） |
| 知识检索 | 参数来自用户问题（`query`） |
| 工具会报错 | 错误回传后模型如何"改口" |

**后端自检（无需 Key 也能看工具说明书）**

```bash
curl http://localhost:8000/api/tools

```

**跑一次真实工具循环**（需要 Key）：

```bash
curl -X POST http://localhost:8000/api/tools/run \
  -H "Content-Type: application/json" \
  -d '{"question":"深圳现在多少度？如果超过 28 度，把它换算成华氏度告诉我。"}'
```

**前端验证清单**

- [ ] 左栏列出 4 个工具，点开 `get_weather` 能看到 `unit` 的 `enum` 是 `celsius/fahrenheit`；
- [ ] 点「单工具」→ 右栏时间线出现 1 个青绿节点，参数是 `{"expression": "(1234+876)*3/7"}`，结果是 `904.2857...`，最终回答正确；
- [ ] 点「并行两工具」→ 同一 `STEP 1` 下**两个**节点（两个 `get_weather`）；
- [ ] 点「连续两轮」→ `STEP 1` 是 `get_weather`、`STEP 2` 是 `calculator`，说明模型会"拿着结果再决策"；
- [ ] 点「工具会报错」→ 节点变琥珀色，`error` 写明"没有 火星 的天气数据"，最终回答是模型在解释而非崩溃；
- [ ] 把 `max_steps` 调成 1（在 `useToolRunner` 的 body 里加上）→ 时间线 1 个节点、最终回答位置显示"达到 max_steps 上限仍未收敛"。

**实测记录（真实调用 DeepSeek-Flash 的结果）**

「连续两轮」预设为什么用**深圳**而不是北京？因为北京是 26℃、不满足"超过 28 度"的条件：

| 问题 | 实测 trace | 模型行为 |
|---|---|---|
| 深圳…超过 28 度就换算 | `STEP1 get_weather(深圳) → 32℃`；`STEP2 calculator("32*9/5+32") → 89.6` | 条件成立 → **两轮链路** |
| 北京…超过 28 度就换算 | `STEP1 get_weather(北京) → 26℃` | 条件不成立 → **只调一个工具**，并回答"26℃ 没有超过 28℃，不需要换算" |

两行都对——这恰好是本阶段最值得玩味的一点：**模型不是机械地"每轮都调工具"，它读得懂条件**。如果你的预设问题在演示时"少了一轮"，先别怀疑代码，看看是不是条件本身不成立。

同理，「并行两工具」（北京 + 上海）实测是**同一个 `STEP 1` 下两个 `get_weather` 节点**，模型一次就把两个查询都发了出来。

> 关于时间线里的 `ms`：它统计的是**工具函数自身的执行时间**（本地函数，通常是 0.0～0.2ms），不含与模型的往返（那通常要 1～3 秒）。所以别看到 `0ms` 就以为"没执行"——参数和结果都在，就是执行过了。

## 6. 小结

- **模型不执行代码**，它只申请；执行权始终在我们手里——这既是安全边界，也是能力边界。
- 工具定义写一遍（Pydantic）就能同时产出 **给模型的 JSON Schema** 和 **运行时校验器**，`Field(description=...)` 是写给模型看的文档。
- 工具循环的两个硬约束：**assistant 消息先写回**、**`tool_call_id` 必须配对**。
- 失败要当数据回传（`{"error": "..."}`），让模型自纠或解释；`max_steps` 是必备的刹车。
- 模型给的参数是不可信输入：`eval` 之外的世界很大，AST 白名单只是最小示例。
- trace 是这一阶段的产品价值：把"模型为什么这么答"摊开，用户才会信任它。
