# 阶段 14 · AI 搜索应用

> 把阶段 07–13 攒下的检索与智能体能力，**产品化**成一个「带出处、可核对」的 AI 搜索——
> 也就是 Perplexity / 文库搜索那种「问一句、给答案、每段挂来源」的体验。
> 本阶段的核心不是「又学会一种检索」，而是学会一个更小但更产品化的问题：
> **怎么让答案变得可被验证。**

---

## 1. 阶段目标

- 理解 **AI 搜索（Grounded Search）** 与传统 RAG 的差异：RAG 输出一段文本，AI 搜索额外输出**每段结论的出处**。
- 掌握**引用工程（citation engineering）** 的两步：① 用提示词逼模型「只依据资料 + 每句标 `[n]`」；② 把模型吐出的 `[n]` **解析、校验、映射回来源**。
- 明确一个关键边界：**「引用了」≠「可信」**——本阶段能验证的只是「模型声称引用了哪几段」，忠实性（faithfulness）留给阶段 15。
- 产出一个完整的前端搜索页：搜索框 → 混合检索 → 带 `[n]` 答案 + 可点击核对的来源面板。

---

## 3. 核心概念

### 3.1 为什么「检索到」不等于「用户相信」

阶段 07–08 的 RAG 链路是：

```
用户提问 → 检索 top-k → 拼进 prompt → 生成
```

用户拿到的是一段**看起来很对、但无法核对**的文字。它有两个隐患，而且都**静默发生**：

1. **断章取义**：top-k 里某段只含半句相关，模型却按自己的理解补全了——用户看答案天衣无缝，看原文才发现对不上。
2. **凭记忆作答**：模型在资料没覆盖的地方，悄悄用训练记忆补了一句，资料里根本没有。

AI 搜索的解法，是给答案**强制挂出处**：每句结论后面写 `[n]`，`n` 指向来源面板里的第 `n` 段。用户点一下就能跳过去核对。这一步把「我相信你」变成「我能验证你」。

### 3.2 引用工程的两步

```
检索 top-k（复用 rag.hybrid_search）
        │
        ▼
合成（prompt 约束：只用资料 + 每句标 [n]）
        │
        ▼
解析 + 校验（正则提取 [n] → 去重保序 → 丢掉越界/非法下标 → 映射回来源）
        │
        ▼
finish：answer（带 [n]）+ sources（每条带 cited 标记）+ grounded
```

**第一步（合成）** 靠提示词纪律：

> 你只依据【资料】回答；每个事实性结论后用 `[n]` 标注引用的资料编号；资料里没有的就说「未提及」，不要编造。

**第二步（解析 + 校验）** 是这一步真正的开关，也是很多教程漏掉的地方——**模型给的编号不能全信**：

- 模型可能写 `[9]`，但本次只检索了 3 段 → 越界，必须丢弃，否则前端按编号定位来源会越界崩溃；
- 模型可能写 `[0]` 或 `[1][1]` → 非法 / 重复，按「1 ≤ n ≤ top_k 且未出现过」过滤；
- 过滤后的编号列表，就是 `citations`；`sources` 里 `cited=true` 的条目，就是答案里 `[n]` 实际指向的来源。

### 3.3 「引用了」≠「可信」

这是本阶段最重要的一句警告。`grounded=true` 只代表：**模型在答案里写了 `[n]`，且 `n` 落在合法来源上**。它不保证：

- 模型真的只用了那几段（它可能还偷偷用了记忆）；
- 那段话真的支持这个结论（可能断章取义）；
- 未被引用的段落里没有更关键的矛盾信息。

这些属于 **忠实性（faithfulness）** 问题，需要额外的「引用归因 / NLI 校验」机制，留给阶段 15 Deep Research。所以前端会把 `grounded` 如实显示，而不是假装「已验证」。

### 3.4 和阶段 13 的关系：引擎 vs 产品外壳

| | 阶段 13 Agentic RAG | 阶段 14 AI 搜索 |
|---|---|---|
| 解决的 | 要不要查、查够了没、不够怎么换着查 | 查回来之后怎么让用户相信 |
| 检索 | 多轮自适应（向量→混合→图谱） | 单轮混合 + 重排（快而准） |
| 输出 | 决策链路时间线 | 带 `[n]` 的答案 + 来源面板 |
| 一句话 | 检索引擎 | 引擎之上的产品外壳 |

两者可以组合：把阶段 13 的 `run_agentic_blocking` 当成「检索器」替换掉本阶段的 `_search_retrieve`，就得到「自适应检索 + 带引用答案」。但本阶段**刻意选单轮混合检索**，理由有二：① 搜索产品要的是即时响应，多轮决策回路是负担；② 让本阶段的 diff 干净——`git diff stage-13 stage-14` 就是「多了一个 `search.py`」。

## 4. 动手实现

### 4.1 后端 `search.py`：三件事收口在一个生成器里

事件协议与阶段 10/11/12/13 统一（一帧一行）：

```
start        问题、模型、topK
retrieve     命中片段 + 数量 + 耗时              ← ① 一次有力检索
synthesize   合成状态（有/无资料）
answer_delta 带 [n] 的答案增量文本             ← ② 带引用的合成
finish       答案 + 来源列表 + citations + grounded ← ③ 引用解析 + 校验
error        失败原因
```

检索直接复用阶段 08，不重新发明：

```python
def _search_retrieve(query, top_k, rerank):
    found = rag.hybrid_search(query, top_k=top_k, mode="hybrid", rerank=rerank)
    hits = [{"title": h["title"], "index": int(h["index"]), "text": h["text"],
             "score": h.get("score"), "rerankScore": h.get("rerank_score"),
             "channel": "hybrid"} for h in found.get("hits", [])]
    return {"hits": hits, "ms": ...}
```

合成段是引用工程的全部重心——提示词里把「只依据资料」「每句标 `[n]`」「不许编造」三条写死：

```python
SEARCH_SYSTEM = (
    "你是一个 AI 搜索回答助手。请只依据下面提供的【资料】回答用户的问题。\n"
    "1. 每个事实性结论后，用 [n] 标注它引用的资料编号；\n"
    "2. 如果多条资料都支持同一句，可以写 [1][2]；编号必须是资料里真实存在的；\n"
    "3. 资料里没有的内容，明确说「资料里未提及」，不要凭记忆补充，也不要编造；\n"
    "4. 回答要直接、结构化，不要复述问题。"
)
```

`finish` 前的解析 + 校验（**这一步最容易被省略，却最该有**）：

```python
_CITE_RE = re.compile(r"\[(\d+)\]")

def _parse_citations(answer, max_n):
    seen = []
    for m in _CITE_RE.finditer(answer):
        n = int(m.group(1))
        if 1 <= n <= max_n and n not in seen:   # 越界/非法/重复 → 丢弃
            seen.append(n)
    return seen
```

`citations` 之外的信息，会顺手算出来：

- `sources[]`：每条来源带 `cited` 标记（答案里出现过它的编号即为真）；
- `grounded`：`bool(citations)`，答案**声称**至少引用了一段；
- `coverage`：被引用段数 / 检索段数，给用户一个「引用覆盖率」的直观数字。

### 4.3 前端：搜索框是签名元素

`useSearch.ts` 把 SSE 帧还原成「答案文本（带 `[n]`）+ 来源列表」，并额外把答案拆成
**文本段 / 引用 chip** 交替的序列，方便模板渲染：

```ts
const answerParts = computed(() => {
  const re = /\[(\d+)\]/g
  // 把 "见[1]和[2]" 拆成 [{text:'见'},{cite:1},{text:'和'},{cite:2}]
})
```

`SearchConsole.vue` 的三块：

1. **搜索框（签名元素）**：大号输入框 + 强调色边框，呼应「实验室工作台上的检索终端」定位；
2. **答案卡**：`[n]` 渲染成可点击的琥珀色 chip，点一下调用 `focusSource(n)` 滚动并高亮来源面板里第 `n` 条；
3. **来源面板**：按「被引用优先、其次检索排名」排序，被引用的来源浮到前面、边框点亮为青绿。

```ts
function focusSource(n: number) {
  activeSource.value = n
  document.getElementById(`src-${n}`)?.scrollIntoView({ behavior: 'smooth', block: 'center' })
}
```

> 视觉区分：阶段 13 的签名是「决策链路」，用冷静的青绿标「留下/丢弃」；阶段 14 的签名是
> 「搜索框 + 引用 chip」，用琥珀强调色标「可点击核对」。两者同属一套设计系统，但记忆点不同。

## 5. 运行验证

### ① 静态冒烟（不需要 Key）

```bash
cd backend && uv run python _t_search_static.py
```

验证五件事，全部通过才算合格：

| # | 验证点 | 期望 |
|---|---|---|
| 1 | 来源面板条数 == top_k，且 `cited` 与答案 `[n]` 一致 | `[1,3]` → 第 1、3 条 `cited=true` |
| 2 | 引用解析去重保序 | `[1][3][1]` → `citations=[1,3]` |
| 3 | 越界引用 `[9]`（只有 3 段）被安全丢弃 | 不崩溃、不越界 |
| 4 | 答案完全不引用时 `grounded=false` | 来源面板全部未引用 |
| 5 | 耗时分项自洽 | `llmMs == synthesize`，`totalMs >= llmMs` |

### ② 真实调用（需要 Key）

启动前后端后打开 `/search`，输入问题即可。下面的实测表来自本机 DeepSeek-Flash 实跑
（知识库 11 篇 / 412 块 / 图谱 320 实体，每次检索 top_k=6 + 重排）：

| 问题 | 检索条数 | 被引用 | grounded | 覆盖率 | 总耗时 / LLM |
|---|---|---|---|---|---|
| RAG 的切块大小一般取多少？为什么要留重叠？ | 6 | [1,4,2] | ✅ | 0.50 | 12.8s / 8.3s |
| 混合检索里 BM25 和向量检索是怎么结合的？ | 6 | [1,5,2,3,4] | ✅ | 0.83 | 16.5s / 15.8s |
| Cross-encoder 重排和向量相似度排序有什么区别？ | 6 | [1,2,3,4,5,6] | ✅ | 1.00 | 17.9s / 17.1s |

观察三点：

1. **三段答案 `grounded` 全为 `true`**——模型确实把每段结论挂到了检索来源上，来源面板可逐条核对。
2. **覆盖率随问题跨度拉开**：只问「切块大小」时只用到 3/6 段（0.50），问到「Cross-encoder」时 6 段全被引用（1.00）。`coverage` 低不等于答得差，只说明答案没用到所有候选——这本身就是有用的信号。
3. **`totalMs` 与 `llmMs` 之差就是检索耗时**（约 1–3s），与阶段 13 的「grade/rewrite 占 LLM 大头」不同——本阶段只有一次合成调用，瓶颈就是这一次 LLM。

> ⚠️ 以上数字来自本机实跑，**没有伪造任何测量数据**。你的环境耗时会有差异，但结构（检索 → 引用 → 覆盖率）应一致。

## 6. 小结

- AI 搜索 = 检索 + **带出处的合成 + 引用校验**。前三阶段攒的检索资产，在这里第一次变成「用户能核对」的产品。
- 引用工程的两步缺一不可：① 提示词逼出 `[n]`；② 正则解析 + 越界校验。第二步是「可被验证」的真正开关。
- **「引用了」≠「可信」**：`grounded` 只证明模型声称引用了，忠实性留给阶段 15。
- 本阶段刻意用单轮混合检索而不是复用阶段 13 的多轮引擎——搜索要的是快，且让 diff 干净。两者可组合，见练习 1。
