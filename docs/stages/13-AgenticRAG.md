# 阶段 13 · Agentic RAG

> 「Agentic」这三个字很容易被理解成"用了智能体"。本阶段想说明的是另一件事：
> **检索从一条固定管道，变成了一个带反馈回路的控制系统。**

---

## 1. 阶段目标

把阶段 07/08 建立的 RAG 管道里**三个被硬编码的决定**，换成三个可以被审视、可以被质疑的决策：

| # | 过去的做法（硬编码） | 本阶段 |
|---|---|---|
| ① | 无论如何都检索 top-k | **先判断要不要检索** |
| ② | 检索到什么就用什么 | **判断检索到的够不够用** |
| ③ | 一次不成就直接生成答案 | **改写检索词、并换一种检索方式重试** |

完成本阶段后你应该能回答：

- 为什么「多查总没错」是错误的直觉？
- 一个静默降质的 RAG，和监督不到位的流水线有什么共同点？
- 为什么"该换哪种检索法"这件事，值得交给模型判断而不是写死？

## 3. 核心概念

### 3.1 固定管道的三个静默缺口

阶段 07 的 RAG 长这样：

```
用户提问 → 无论如何都检索 top-k → 拼进 prompt → 生成
```

它有三个问题，而且**共同点是都不会报错**：

1. **不该查的也查**：问「1+1 等于几」照样去向量库捞一圈。捞回来的东西既浪费 token，
   还可能把模型带偏——**噪声也是会影响答案的**。
2. **检索失手没人知道**：召回错了 top-k，答案就悄悄降质。没有错误、没有警告，
   只有一个看起来很正常的回答。
3. **没人问过"够不够"**：从没有人（也没有程序）判断过这几段到底能不能支撑一个完整回答。

⭐ **静默失败比崩溃更难对付。** 崩溃会被立刻发现；悄悄降质会一路活到线上，
直到某个用户拿着错的答案来做决策。

### 3.2 三个决策点，三种"省"

```
                ┌─────────────┐
用户提问 ─────▶ │ ① route     │─── 无需检索 ──▶ 直接生成 ──▶ 答案
                │  要不要检索？│
                └──────┬──────┘
                       │ 需要
                       ▼
                ┌─────────────┐
                │ 检索（第 N 轮）│
                └──────┬──────┘
                       ▼
                ┌─────────────┐
                │ ② grade     │─── 够用 ──▶ 生成 ──▶ 答案
                │  够不够？    │
                └──────┬──────┘
                       │ 不够（且还有轮次）
                       ▼
                ┌─────────────┐
                │ ③ rewrite   │─── 改写检索词
                │  怎么重试？  │─── 并换一种检索方式 ──▶ 回到"检索"
                └─────────────┘
```

每一步省下的东西是不同的：

- ① 省下的是**不该花的钱**（token 与延迟）
- ② 省下的是**悄悄降质的答案**
- ③ 省下的是**一次失手就认命**

### 3.3 ⭐ 被反思的不只是检索词，还可以是"检索方式"

这是本阶段最值得记住的一点。多数 Agentic RAG 的实现只做「改写 query」，
本阶段让**检索通道本身也跟着轮次升级**：

| 轮次 | 通道 | 来自 | 适合什么 |
|---|---|---|---|
| 第 1 轮 | 纯向量 | 阶段 07 | 语义相近优先，最便宜，先试一轮 |
| 第 2 轮 | 混合 + Cross-encoder 重排 | 阶段 08 | 向量漏掉的**关键词**在这里补回来 |
| 第 3 轮 | 知识图谱 | 阶段 09 | 换成关系视角，适合**多跳 / 关系型**问题 |

好处是双重的：前三阶段的检索资产各归其位（而不是被一个"更强的模型"替代），
并且用户能预判"下一轮会看到什么"。

> 对照一下"给 ReAct 加个检索工具"那条路：模型确实**能**决定要不要搜，
> 但"检索质量"这件事仍然只存在于它的上下文里——外部不可见、不可复盘。
> 本阶段刻意把评级和改写做成独立步骤：**代价是多几次 LLM 调用，换来每一步都可观测。**

### 3.4 ⚠️ 反模式：把三个决策又塞回一个 prompt 里

最省事的写法是给模型一大段指令，让它一次性输出"要不要查 + 查得怎样 + 下一步怎么办"。
不要这么做——理由是阶段 04 那条经验的延长线：

> **模型输出一旦自由发挥，解析就成了下游的泥潭。**

本阶段每个决策点各自一个 system 提示词、各自的 Pydantic 模型，全部收口到同一个
`_json_call`（JSON 模式 + 校验 + 一次自纠）。**决策之间的接口要像函数签名一样硬。**

## 4. 动手实现

### 4.1 三个决策的数据结构

```python
class RouteDecision(BaseModel):
    needRetrieval: bool          # ① 要不要检索
    reason: str = ""             #    一句话理由（给用户看，不是给日志看）

class GradeVerdict(BaseModel):
    useful: bool                 # ② 综合起来够不够
    keep: list[int]              #    哪些片段真的有用
    missing: str = ""            #    具体还缺什么（禁止写"信息不足"这种空话）

class RewritePlan(BaseModel):
    query: str                   # ③ 改写后的检索词
    why: str = ""
```

`missing` 这一项看着不起眼，其实是整个回路能不能闭环的关键：**改写员要知道往哪个方向改**，
否则第二轮只是换个说法再撞一次运气。

### 4.2 主流程（`backend/agentic.py`）

```python
def run_agentic(client, question, *, max_rounds=3, top_k=3, ...):
    yield {"type": "start", ...}

    # ① 要不要检索
    decision, raw = _json_call(client, [...], RouteDecision, ROUTE_HINT)
    yield {"type": "route", "needRetrieval": ..., "reason": ...}

    if not decision.needRetrieval:
        for piece in client.stream([DIRECT_SYSTEM, question], ...):
            yield {"type": "answer_delta", "text": piece}
        yield {"type": "finish", "rounds": 0, "basedOn": "none", ...}
        return                      # ⭐ 整条检索链路被跳过

    # 检索 → 评级 → 改写 的反馈回路
    for round_no in range(1, max_rounds + 1):
        channel = CHANNELS[min(round_no - 1, len(CHANNELS) - 1)]  # 通道升级
        hits = _retrieve(channel, query, top_k, hops)
        yield {"type": "retrieve", "round": round_no, "channel": ..., "hits": hits, ...}

        verdict = _json_call(client, _grade_messages(question, hits), GradeVerdict, ...)
        yield {"type": "grade", "round": round_no, "useful": ..., "kept": keep, ...}

        if verdict.useful and keep:
            break                   # ⭐ 够用就收手，不白跑第二轮
        if round_no == max_rounds:
            break

        plan = _json_call(client, [...], RewritePlan, ...)
        yield {"type": "rewrite", "from": query, "to": plan.query, ...}
        query = plan.query          # 下一轮用改写后的词
```

### 4.3 ⭐ 三处降级：`_json_call` 失败时怎么办

这三个决策点都可能失败（模型吐出非法 JSON）。处理方式**刻意不同**，这是本阶段一个容易被忽略的设计点：

| 决策点 | 解析失败时的处理 | 为什么这么选 |
|---|---|---|
| ① route | **降级为"照常检索"** | 少查的风险 > 多查的风险。降级后行为等价于阶段 07，**不会更差** |
| ② grade | **保守地全部留下** | 宁可让人来判断，也不擅自丢弃资料 |
| ③ rewrite | **沿用原检索词** | 改写本身是优化项，失败不值得中断流程 |

共同点：**降级的目标都是"退化到前一个阶段的行为"，而不是崩溃、也不是假装成功。**
阶段 04 里我们学的是"解析失败就如实报错"——这里不同，因为这些失败**不阻塞主流程**。

### 4.4 ⭐ 先归一，再评级

三个通道的返回原本各不相同（`hybrid_search` 给 `score` 和一堆 `_rank`，
`graph_search` 给 `chunks` + `edgeCount`）。`_retrieve` 统一归一成：

```python
{"title": str, "index": int, "text": str, "score": float | None, "channel": str}
```

不归一的话，后面的**评级**和**引用**就得为每个来源各写一份分支——那才是真正的技术债。
归一这一步的成本是一次字典推导，收益是下游全部保持单形态。

### 4.5 ⚠️ 一处有意的技术债（已记账）

`_json_call` / `_strip_fence` / `_validation_hint` 与 `team.py` 里的同名逻辑重复。

阶段 12 定过规矩：**一份逻辑出现第三次，才值得抽成框架**。agentic 是第三处了，本该抽。
但抽到 `llm.py` 会波及阶段 11 已发布的代码与两处桩测试，**收益不抵风险**。

所以本文件自带一份紧凑实现，并把这个决定写进了模块顶部的 `TECH_DEBT` 注释里，
注明"下一处再需要时应连同 team.py 一起下沉"。

> 记技术债和欠技术债是两件事。**写下来的债是可控的，没写下来的才会变成意外。**

### 4.6 后端端点

| 端点 | 作用 |
|---|---|
| `GET /api/agentic/channels` | 通道清单 + 每个通道在第几轮（`why` 字段说明为什么在这一轮） |
| `POST /api/agentic/run` | 非流式，返回答案 + `timeline`（retrieve / grade / rewrite 分组） |
| `POST /api/agentic/stream` | 流式，逐帧推 `route / retrieve / grade / rewrite / answer_delta / finish` |

### 4.7 前端：`useAgentic.ts` + `AgenticConsole.vue` + `/agentic`

⚠️ **没有复用阶段 11/12 的 `AgentColumn`**，这是刻意的。

那边的时间线是"一个角色的 Thought / Action / Observation"，
这里的时间线是"轮次驱动的决策结构"（每轮含 retrieve + grade + 可选 rewrite）。
形状不同，硬套会让视图层写满分支。

> **复用要复用在同一个抽象层级上——错层复用比重复代码更贵。**

所以 `useAgentic` 自己维护一个 `rounds: AgenticRound[]`，把 SSE 帧还原成嵌套的回合结构，
视图只要 `v-for` 即可。

## 5. 运行验证

### ① 静态桩测试（不需要 Key，可重复回归）

```bash
cd backend && .venv/Scripts/python.exe _t_agentic_static.py
```

断言五条不变量：

| # | 不变量 | 它在防什么 |
|---|---|---|
| 1 | 无需检索时，事件流里**不出现** retrieve/grade/rewrite | 防止"无论如何都查一遍" |
| 2 | 第一轮够用时不进第二轮 | 防止无谓的 token 浪费 |
| 3 | 评级不足时确实 rewrite，且第 2 轮通道是 `hybrid` | 保证反馈回路真的闭环 |
| 4 | 三轮都不够也能收尾，耗时分项自洽 | 防止死循环 / 伪造的耗时数字 |
| 5 | 通道清单与 `CHANNELS` 一致且每轮有理由 | 防止计划与实际执行漂移 |

> ⭐ 桩 client 按 **system 提示词** 分流（四个决策点各有一段 system），
> 所以同一段业务代码不需要任何改动就能被确定性驱动——这是阶段 11 `ScriptedClient` 的思路复用。
> 另外测试里把 `_retrieve` 换成了确定性桩：**本测试验的是决策链路，不是底层检索准不准**
> （那是阶段 07/08/09 各自的事）。不替换的话结论会随本机向量库状态漂移。

### ③ 关键对照

在同一个问题上，把本阶段的控制台与阶段 08 的混合检索台并排跑一次，你会看到：

- 阶段 08 永远检索，本阶段可能一步都不检索；
- 阶段 08 一次定生死，本阶段最多问自己三次"够不够"；
- 本阶段多花的 LLM 调用（路由 + 评级 + 可能的改写）**换来了每一步都可解释**。

## 6. 小结

- Agentic RAG 的实质不是"用了智能体"，而是**把检索改成了带反馈回路的控制系统**。
- 三个决策点分别省下三种不同的东西：不该花的钱、悄悄降质的答案、一次失手就认命。
- **被反思的不只是 query，还可以是检索方式本身**——这让前三阶段的资产各归其位。
- 降级策略的目标永远是"退化到前一阶段的行为"，而不是崩溃或假装成功。
- 记下来的技术债是可控的债；把 `_json_call` 与 `team.py` 的重复写进注释，比悄悄留着强。
- 复用要在同一个抽象层级上进行——因此本阶段没有硬套 `AgentColumn`。

## 7. 练习与验收

**练习（改造题）**：给 `CHANNELS` 增加第四轮 `ask_user`：当三轮都失败时，不再硬着头皮回答，
而是向用户反问一句"你指的是 X 还是 Y？"。思考这需要在数据模型里加什么字段、
以及在 SSE 帧协议里新增哪一类帧。

**延伸思考**：本阶段的评级员会和 Critic（阶段 11 的评审员）撞车吗？
如果要在主流程里同时用两者，你会怎么分配职责？（提示：一个评"资料够不够"，
一个评"结论有没有被资料支撑"——**它们看的是不同对象**。）

**验收标准**：

1. `_t_agentic_static.py` 五条断言全绿。
2. `_t_team_static.py` 与 `_t_harness_static.py` 仍全绿（本阶段未改动既有循环）。
3. `import main` 能成功（**历史教训：曾经 `Harness*` 三个模型忘了 import，
   导致整个后端起不来，而桩测试一个都没报错**）。
4. `/agentic` 页面上，问「1+1 等于几」时**不出现任何检索事件**。
5. `vue-tsc -b` 0 错误，`vite build` 通过，`pnpm docs:build` 通过。

**调试题**：若 MTV 的时间线里只有 `finish` 没有 `route` —— 先确认前端 `apply()`
是不是漏了 `case 'route'`（本协议每帧都必须有 `type`，帧类型拼错会被 `default` 静默吞掉，
表现是"链路缺一块但不报错"）。
