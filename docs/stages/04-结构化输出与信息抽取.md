## 3. 核心概念

### 3.1 JSON 模式 ≠ 合规保证

OpenAI/DeepSeek 都支持 `response_format={"type": "json_object"}`：模型被约束只输出**合法的 JSON 字符串**。但"合法 JSON"只是第一道闸门，schema 合规还需要：

- 字段**名**得对（`title` 不能写成 `标题`）
- 字段**类型**得对（`birth_year` 拿到的是数字，不是字符串 `"1992"`）
- **必填**不能少
- **枚举**必须落在候选集合里（`sentiment` 只能是 `positive/neutral/negative`）

这些都不是 JSON 模式能管的事。本阶段的三件套就是：

```
JSON 模式   让模型愿意输出 JSON
Pydantic   运行时校验 JSON 是否符合 schema
自纠重试   校验失败 → 把错误原因塞回去 → 让模型改
```

### 3.2 动态 Pydantic 模型：把字段定义编译成校验器

Pydantic v2 提供 `pydantic.create_model("Name", field1=(str, ...), field2=(int, None))`，可以**在运行时**根据前端的字段定义拼出一个模型。这比维护一套"内置模型"灵活得多——前端想抽什么字段都行。

我们做了三件事：

- `name` 用 `Field(pattern=r"^[A-Za-z_][A-Za-z0-9_]*$")` 限定成合法标识符——这是 `create_model` 的硬要求，否则直接报错。
- `enum: list[str]` 仅对 `type="string"` 生效，用 `Literal[tuple(values)]` 编译成"枚举约束"。
- `required=False` 用 `(Optional[T], None)` 表示，校验时缺失值 → 合法，类型不对 → 非法。

Pydantic v2 默认 `extra="ignore"`：模型偶尔塞进几个声明外的字段（比如 `id` 或 `extra`），不会因此抛错，只把声明字段纳入最终 `data`。

### 3.3 自纠重试：把错误原因喂回去

LLM 失败时常见的工程反应是"加更多 prompt 让它守规矩"，但更稳的套路是**让模型看到自己错在哪**：

```
[user]   字段: - title (string, 必填): ...\n----- 文本 -----\n...
[assistant] {"标题": "嫦娥七号..."}              ← 第一次：字段名错
[user]   你的上一次响应未通过 schema 校验：
         title: Field required（期望类型 string）
         请修正并只输出合法 JSON。
[assistant] {"title": "嫦娥七号...", ...}        ← 第二次：按反馈改
```

我们最多重试一次（2 次尝试）。再多的重试边际收益迅速衰减，且会显著增加 token 与延迟。

### 3.4 厂商能力差异：能降级就别抛 500

`response_format={"type":"json_object"}` 不是一个"标准能力"。DeepSeek-V3 / Flash 兼容，但换成某些厂商会直接 400。本阶段的做法：

```python
try:
    raw = client.chat(messages, response_format={"type": "json_object"})
except BadRequestError as e:
    if "response_format" in str(e) or "json_object" in str(e):
        raw = client.chat(messages)  # 降级：不要 response_format
        warning = "当前模型不支持 JSON 模式，已降级为自由生成"
    else:
        raise
```

**降级并不意味着放弃校验**——后端仍然用 Pydantic 兜底，校验照样会跑、失败照样会自纠。把 `warning` 透回前端，让用户知道这一次的"合规保障降了一档"。

### 3.5 为什么结构化输出一般不用流式

流式的价值是"看到第一个字就开渲染"，但结构化输出的下游消费者是**机器**（Pydantic、数据库、表格），它必须拿到完整 JSON 才能解析与校验。如果半截 JSON 流进来会一直解析失败，反而徒增复杂度。所以阶段 04 没有 `/api/extract/stream`——一次拿完整再校验是正确做法。

## 4. 动手实现

### 4.1 后端 · 契约：`schemas.py`

```python
class FieldSpec(BaseModel):
    name: str = Field(min_length=1, pattern=r"^[A-Za-z_][A-Za-z0-9_]*$")
    type: Literal["string", "int", "number", "bool", "array"]
    description: str = ""
    required: bool = True
    enum: list[str] | None = None

class ExtractRequest(BaseModel):
    text: str = Field(min_length=1)
    fields: list[FieldSpec] = Field(min_length=1)
    model: str | None = None

class ExtractResponse(BaseModel):
    data: dict | None = None
    raw: str = ""
    attempts: int = 1
    valid: bool = False
    model: str
    error: str | None = None
    warning: str | None = None
```

要点：`name` 的正则限定是**强制约束**，因为后续 `create_model` 会把它当作属性名——非法标识符会让整条请求失败，提早挡在上游比抛 500 体面。

### 4.2 后端 · 抽取引擎：`extract.py`

三段函数分别承担"建模 / 提示 / 执行"。

```python
def build_model(specs: list[FieldSpec]) -> type[BaseModel]:
    fields: dict[str, Any] = {}
    for spec in specs:
        ann = _annotation(spec)                          # 类型映射 + Literal
        fields[spec.name] = (ann, ...) if spec.required else (Optional[ann], None)
    return create_model("Extraction", **fields)
```

```python
def _build_messages(text: str, specs: list[FieldSpec]) -> list[dict]:

    # DeepSeek 的 json_object 模式要求 prompt 中含 "json" 字样，这里已满足
    ...
```

```python
for attempt in (1, 2):
    try:
        raw = client.chat(messages, response_format={"type": "json_object"})
    except BadRequestError as e:
        if "response_format" in str(e) or "json_object" in str(e):
            raw = client.chat(messages)
            warning = "已降级为自由生成"
        else:
            raise
    try:
        parsed = model_cls.model_validate_json(raw)
        return ExtractResponse(data=parsed.model_dump(), valid=True, ...)
    except ValidationError as ve:
        # 自纠：把错误原因塞回 messages，再答一次
        messages += [
            {"role": "assistant", "content": raw},
            {"role": "user", "content": f"未通过 schema 校验：{_validation_hint(ve)}\n请修正并只输出合法 JSON。"},
        ]
return ExtractResponse(data=None, valid=False, error=...)
```

`_validation_hint` 把 Pydantic 的 `ValidationError` 压缩成对模型友好的中文短语（如 `title: Field required（期望类型 string）`），太长反而会让模型困惑。

### 4.3 后端 · 路由：`main.py`

```python
@app.post("/api/extract", response_model=ExtractResponse)
def extract(req: ExtractRequest) -> ExtractResponse:
    client = get_client()
    try:
        return extract_one(client, req)
    except Exception as e:
        raise HTTPException(status_code=502, detail=f"抽取失败：{e}") from e
```

注意：**校验失败不会 5xx**——返回 `valid=False` + `error` 让前端照原样展示。这是有意的：失败也是这一轮的结果。

### 4.4 前端 · `useExtractor.ts`

`PRESETS` 给两个"开箱即用"场景（新闻 / 简历），让你点一下预设就能立刻体验"输入一段文本 + 字段定义 → 得到结构化结果"的完整闭环。`payload` 把前端字段定义映射到后端契约：

```ts
{ name, type, description, required,
  enum: f.type === 'string' && f.enum.length ? f.enum : null }
```

`canRun` 守住"文本非空 + 字段非空 + 不在加载中"。

### 4.5 前端 · `Extractor.vue`

三栏网格（≥1100px 时）：

- **左**：待抽取文本（mono 等宽，方便看清标点）。
- **中**：字段定义（动态行：name / type / description / required / enum 输入 / 删除按钮）+ 「抽取并校验」+ 状态徽章 `✓ 通过 · 第 N 次` / `✗ 失败 · N 次尝试`。
- **右**：结果——成功时表格化（值是数组用 chip 渲染）、失败时高亮 `error` + 折叠的 `raw`；`warning` 单独琥珀条提示。

状态徽章 + chip 配色延续设计系统：**Data 青绿 = 通过 / 单个数组元素**，**Signal 琥珀 = 警告 / 失败**。

`details/summary` 折叠原始 JSON——成功时方便复盘"模型到底答了啥"，失败时方便定位"是不是 prompt 没说清"。

**实测记录（真实调用 DeepSeek-Flash）**

用「新闻」预设的 6 个字段（含 `sentiment` 枚举）抽取一段航天新闻，**一次通过**：

| 项 | 实测值 |
|---|---|
| `valid` / `attempts` | `true` / `1`（未触发自纠） |
| `title` | 嫦娥七号成功完成环月轨道修正 |
| `source` / `date` | 新华社 / `2026-03-15` |
| `tags` | `["嫦娥七号","国家航天局","月球探测","近月制动","月球科研站"]` |
| `sentiment` | `positive`（落在枚举内） |
| 耗时 | 约 0.9s |

两个值得注意的点：

1. 原文写的是"**2026 年 3 月 15 日**"这种中文日期，模型把它规范成了 `2026-03-15`——这正是"在字段 `description` 里写清格式（`发布日期 YYYY-MM-DD`）"的回报。**字段描述就是 Prompt**。
2. 一次通过不等于"不需要校验"：`attempts=1` 只是说这次模型答对了，而**校验器永远在场**——它决定"这次算不算答对"。想亲眼看到自纠，就把某个字段的 `required` 打开而让模型拿不到数据（例如问一段完全无关的文本要 `date`）。

## 6. 小结

- **JSON 模式只是「倾向」，不是「合规」**：所有"严格字段约束"都得由运行时校验器（这里是 Pydantic）兜底。
- **动态 Pydantic 模型**让"字段定义在前端、模型在后端"这种灵活 UI 成为可能，且仍保留强类型校验。
- **自纠重试**比"在 prompt 里多训一句"稳得多——把具体错误作为消息喂回去，模型基本都能改对。
- **厂商差异是真实问题**：JSON 模式降级路径是必备的兜底，"降级而不放弃校验"是工程态度。
- **失败也是结果**：后端返回 `valid=False` + `error` + `raw`，前端原样展示，让用户能复盘为什么失败。
- 设计系统延续：Mono 字体呈现 JSON、Data 青绿 = 通过、Signal amber = 警告 / 失败，状态徽章与 chip 让结果区一眼可读。
