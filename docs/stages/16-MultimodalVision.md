# 阶段 16 · 多模态·图像

> 前面十五个阶段，模型看到的都只有**文字**。本阶段把图片也变成一种输入。
> 但它真正的知识点不是「模型能看图」——而是：
> **让模型看图的秘密不在模型调用，而在消息结构。**
> 阶段 03 起 `client.chat()` 收的就是 `messages`，我们只是把其中一条 user 消息的
> `content` 从「字符串」换成了「数组」——协议层零改动，`llm.py` 一行没动。

---

## 1. 阶段目标

- 理解**多模态输入**的工程本质：它不是接入了一个新模型，而是**输入编码**的一次扩展——把图像的字节编码进消息的 `content`。
- 掌握 OpenAI 兼容协议的图像消息结构：`content` 由字符串升级为**块数组**
  （`{"type":"text"}` + `{"type":"image_url","image_url":{"url": <data URL>}}`），并理解 `detail` 的作用。
- 学会**服务端先做确定性解析**：用**魔数**（文件头固定字节）判断真实格式，而不是相信文件名或 data URL 里声明的 mime；顺带校验格式白名单与体积上限、从文件头读出尺寸。
- 打通两条产品路径：**视觉问答（qa）**——看图回答一个问题；**结构化抽取（extract）**——把图里的信息抽成字段表（复用阶段 04 的「JSON + 校验 + 一次自纠」）。
- 产出一个完整的前端页面：拖入 / 粘贴 / 点选图片 → 预览与「图像体检单」→ 流式回答或字段表。

---

- **复用资产**：`llm.LLMClient`（`stream` / `chat`，**本阶段对其零改动**）、阶段 04 的「JSON + Pydantic 校验 + 一次自纠」招式（本文件自带一份紧凑实现）。

## 3. 核心概念

### 3.1 「能看图」的秘密在消息结构，不在模型调用

阶段 03 起，我们一直在发这样的消息：

```python
{"role": "user", "content": "你好"}          # content 是【字符串】
```

多模态只改一处——`content` 变成**块数组**：

```python
{"role": "user", "content": [
    {"type": "text",      "text": "这张图里有哪些数据？"},
    {"type": "image_url", "image_url": {"url": "data:image/png;base64,iVBOR...", "detail": "auto"}},
]}
```

就这一处。`LLMClient._payload()` 原样转发 `messages`，所以**整个 `llm.py` 不需要任何改动**。
理解这一点，多模态就从「神秘的模型能力」还原成了一个**输入编码格式**：

```
图片字节 ──base64──▶ data URL ──塞进 content 数组──▶ messages ──▶ 同一个 chat/completions
```

### 3.2 为什么要先在服务端做「确定性解析」

把图片交给模型之前，服务端先做一件**不需要模型**的事：解出图片的客观属性。

```
data URL / base64
      │
      ├─ ① 拆出 base64 并解码
      ├─ ② 魔数嗅探：真实格式是什么（不信任声明的 mime）
      ├─ ③ 白名单校验：PNG / JPEG / GIF / WebP，其余拒绝
      ├─ ④ 体积上限：> 8 MB 直接拒，不把请求撑爆
      └─ ⑤ 读文件头拿尺寸
      ▼
{ format: "png", width: 760, height: 460, bytes: 52305, mismatch: false }
```

这三件事**都不该问模型**——它们有确定答案，而且必须在花钱之前就做完：

| 要挡住的东西 | 怎么挡 |
|---|---|
| 改了扩展名 / data URL 里乱写 mime | **魔数**（`\x89PNG\r\n\x1a\n` 等）说了算 |
| 一张 50 MB 的图撑爆请求 | 先量字节，超上限直接 400 |
| 伪装成 `.png` 的脚本 | 魔数不匹配 → 无法识别的格式 |

这正是本项目一贯的**「确定性工程流水线 + LLM」**分工：**能算的别问模型**。

> 本阶段的实现还顺手做了个教学彩蛋：如果 data URL **声明**的 mime 与**魔数**嗅探结果不一致，
> 会在响应里把 `mismatch` 标为 `true`，前端以「体检单」形式红字提示。
> 这是「不信任输入声明」这条安全原则**可见的证据**。

### 3.3 两种输出：qa 与 extract

| | `qa`（视觉问答） | `extract`（结构化抽取） |
|---|---|---|
| system 提示词 | `VIS_SYSTEM`：**只依据图中可见内容**作答，看不到就直说 | `EXTRACT_SYSTEM`：抽成 `label/value` 字段表，禁止推测 |
| 输出 | 一段自然语言（**流式**） | 一段 JSON → 解析成字段表 |
| 前端渲染 | 解读卡片 | 两列表格 + 可折叠的原始 JSON |
| 复用 | —— | 阶段 04 的「JSON + 校验 + **一次自纠**」 |

两条路径共用同一个生成器 `run_vision()`，只在最后一步分岔——这也是本阶段在工程上最省的地方。

### 3.4 和前面阶段的关系

| | 输入 | 输出 | 一句话 |
|---|---|---|---|
| 阶段 03–15 | 只有文字 | 文字 / 结构化 / 报告 | 把文字这件事做到极致 |
| **阶段 16** | **文字 + 图片** | **回答 / 字段表** | **同一套协议，多了一种输入编码** |

关键结论：**多模态不是「新架构」，而是「新编码」**。前面十五个阶段的 SSE 协议、端点接法、composable 结构，本阶段全部照搬。

## 4. 动手实现

### 4.1 后端 `vision.py`：四步走

事件协议延续阶段 10–15 的「一帧一行」，并新增 `structured` 一类：

```
start        模式、模型、图像元数据（格式/尺寸/字节数/声明 mime 是否不符）
answer_delta 流式增量（qa：解读正文；extract：JSON 原文）
structured   extract 模式的解析结果（字段表 + 概括）        ← 阶段 16 新增
finish       完整结果 + 元数据 + 耗时
error        失败原因
```

**① 确定性解析**（见 §3.2）。核心是「魔数优先」：

```python
def _sniff(data: bytes) -> str | None:
    if data[:8] == b"\x89PNG\r\n\x1a\n": return "image/png"
    if data[:3] == b"\xff\xd8\xff":      return "image/jpeg"   # JPEG 有多个 SOI 变体
    if data[:6] in (b"GIF87a", b"GIF89a"): return "image/gif"
    if data[:4] == b"RIFF" and data[8:12] == b"WEBP": return "image/webp"
    return None
```

尺寸读取四种格式各不同（PNG 大端 u32；GIF 小端 u16；**JPEG 要遍历段找 SOF**；WebP 还分 VP8/VP8L/VP8X 三种读法），
读不出就**如实返回 `None`**——而不是猜一个。

**② 拼多模态消息**——全阶段最关键的一行：

```python
def build_messages(img, question, mode, schema_hint, detail):
    return [
        {"role": "system", "content": VIS_SYSTEM},
        {"role": "user", "content": [                                    # ← content 是【数组】
            {"type": "text", "text": text},
            {"type": "image_url", "image_url": {"url": img["dataUrl"], "detail": detail}},
        ]},
    ]
```

**③ 调用**：还是 `client.stream(messages, ...)`，**一个字都没改**。

**④ 分岔**：`extract` 模式把流式的 JSON 文本解析成字段表；解析失败就用**一次自纠**（把坏输出回传、要求严格重来）：

```python
def _extract_with_repair(client, messages, answer, model, temperature):
    parsed = _parse_extract(answer)
    if parsed is not None:
        return parsed                                   # 一次就成功
    fix = messages + [{"role": "assistant", "content": answer},
                      {"role": "user", "content": f"你的输出不是合法 JSON，请严格按此重来：\n{EXTRACT_HINT}"}]
    ...                                                  # 自纠通道失败就如实放弃，不阻塞主流程
```

### 4.2 端点 `main.py`：非法图片返回 400，而不是 502

```python
@app.post("/api/vision/run",    response_model=VisionResponse)   # 非流式
@app.post("/api/vision/stream")                                  # 流式（前端用这个）
```

这里有一个值得注意的**错误语义**区分：`vision.VisionInputError`（图片不合法）→ **400**（是**你**的问题），
其余异常 → **502**（是**上游**的问题）。流式端点还会在**开流之前**先校验一次，
否则错误就只能以迟到的帧形式出现：

```python
try:
    vision.parse_image(req.image)          # 先校验
except vision.VisionInputError as e:
    raise HTTPException(status_code=400, detail=str(e)) from e
# 校验通过，才创建 StreamingResponse
```

### 4.3 前端：图画布是签名元素

`useVision.ts` 把 SSE 帧还原成：**图像体检单**、**流式回答**、**字段表**。`VisionConsole.vue` 的四块：

1. **图画布（签名元素）**：虚线投递区，支持**拖入 / 粘贴 / 点选**；选中后显示带「蓝图角标」的预览框；
2. **模式分段控件**：`视觉问答` / `结构化抽取`，品红高亮——本阶段的记忆点；
3. **图像体检单**：格式 / 尺寸 / 体积 / 真实 mime；声明与魔数不符时红字警告；
4. **结果区**：qa 走流式解读卡；extract 走两列字段表 + 概括 + 可折叠原始 JSON。

> 视觉区分：阶段 13 青绿（决策链路）、14 琥珀（搜索框）、15 紫（研究大纲）、
> **16 品红（图画布）**。同一套设计系统，四种记忆点。

### ② 真实调用（需要 Key）

用 Pillow 渲染了一张中文**差旅费用报销单**（760×460 PNG，52,305 字节），
跑同一张图的两种模式（本机 DeepSeek 实跑）：

| 指标 | qa（视觉问答） | extract（结构化抽取） |
|---|---|---|
| 提示词 | 「报销人是谁？合计金额是多少？一共列了几条费用明细？」 | 「抽取表头字段 / 每条费用明细 / 合计金额」 |
| 输出 | 3 行要点，62 字 | **18 个字段**（`label/value`） |
| 解码耗时（确定性） | 2.24 ms | 2.04 ms |
| 模型耗时 | 1346.29 ms | 2037.55 ms |
| 总耗时 | 1348.62 ms | 2040.30 ms |

**qa 的回答（原样）**：

```
- 报销人：林晓
- 合计金额：2,158.50 元
- 费用明细：共 3 条（高铁票（往返）、住宿费（2 晚）、市内交通）
```

**extract 抽出的字段（节选）**：

| label | value |
|---|---|
| 单据标题 | 差旅费用报销单 |
| 报销单号 | BX-2026-0917 |
| 报销人 | 林晓 |
| 所属部门 | 平台研发部 |
| 提交日期 | 2026-09-21 |
| 审批状态 | 待审批 |
| 费用明细-项目1 / 金额1 / 备注1 | 高铁票（往返） / 1,240.00 / 二等座 |
| 费用明细-项目2 / 金额2 / 备注2 | 住宿费（2晚） / 760.00 / 协议酒店 |
| 费用明细-项目3 / 金额3 / 备注3 | 市内交通 / 158.50 / 打车 |
| 合计金额 / 币种 | 2,158.50 / 人民币 |

观察四点：

1. **表格结构被完整还原、数字零误差**：18 个字段把「3 行明细 × 3 列 + 6 项表头 + 合计与币种」全抽了出来，
   金额 `1,240.00 / 760.00 / 158.50` 与合计 `2,158.50` 一字不差——**包括中文、千分位、连字符单号**。
2. **确定性解码几乎不花时间**：2.0–2.2 ms，而模型要 1.3–2.0 s。**「能算的别问模型」在这里有了具体数量级**：
   解码是毫秒级，模型是秒级，差了三个数量级。
3. **qa 严格按题意作答、没有脑补**：它只回答了被问的三件事，没有顺手把整张单子复述一遍，
   也没有把「待审批」脑补成「已通过」——`VIS_SYSTEM` 里那句「只依据图中实际可见的内容」起了作用。
4. **⚠️ 抽取结果的「形状」不完全可控**：模型把明细行**自行扁平化**成了
   `费用明细-项目1 / 金额1 / 备注1`，而不是嵌套成 `[{项目,金额,备注}, ...]`。
   这不是错误，而是提醒：**`extract` 模式要容忍字段名与结构随提示词、图片而变**；
   若要严格结构，就得靠阶段 04 那套「动态字段定义 + Pydantic 校验」把形状约束死。

> ⚠️ 以上数字与文本来自本机实跑（Pillow 渲染图片 + DeepSeek 真实调用），**没有伪造任何测量数据**。
> 你的环境耗时会有差异，但结构（先解码 → 再调用 → 分流 qa/extract）应一致。

## 6. 小结

- 多模态的本质是**输入编码**的扩展，不是新架构：把 user 消息的 `content` 从字符串换成**块数组**，
  `llm.py` 与整套 SSE 协议**零改动**。
- **确定性解析先行**：魔数识破伪造格式、体积上限挡掉超大图、文件头读出尺寸——
  这三件事必须在**花钱之前**做完，是「能算的别问模型」的又一次体现。
- 两条产品路径共用同一个生成器：`qa` 出流式回答，`extract` 出字段表（复用阶段 04 的 JSON + 自纠）。
- **`extract` 的输出形状不完全可控**（模型会自行决定怎么扁平化）——要严格结构就必须上 Pydantic 约束。
- 错误语义要分清：**输入非法 → 400**，**上游失败 → 502**。

## 7. 练习与验收

**练习 1（扩展题）**：给 `extract` 模式加一层**「形状约束」**——
允许前端像阶段 04 那样传入字段定义（`[{name, type, required}]`），服务端据此动态生成 JSON Schema
并做 Pydantic 校验（失败时同样走一次自纠）。思考：为什么这次约束比阶段 04 更难？
提示：**图片里的内容不是你能选的**，表里可能根本没有某个字段。

**练习 2（思考题）**：现在的 `dataUrl` 是把图片 base64 后**内联**进 JSON 的，一张 8 MB 的图会变成约 10.7 MB 的请求体。
若要支持多图 / 大图，有哪些工程改法？（提示：对象存储 + 短期签名 URL、先缩放再编码、`detail=low` 降采样。）
思考「**传输成本 vs 精度**」这条权衡该由前端还是后端决定。

**练习 3（改造题）**：把 `qa` 模式改造成**多轮看图对话**（复用阶段 03 的 messages 全量回放）——
用户在看完图后继续追问「那第 3 条明细的备注是什么？」。注意：图片块要不要每轮都重发？
为什么「每轮重发」反而可能是更省事的选择？（提示：服务端无状态。）

**验收标准**：

1. `uv run python _t_vision_static.py` 全绿；`import main` 成功、路由数增加（**47 → 49**）、
   `vue-tsc -b` 零错误、`vite build` 通过、`vitepress build` 通过。
2. 前端 `/vision` 能跑通：拖入 / 粘贴 / 点选一张图片能在本地预览；体检单显示格式与尺寸；
   `qa` 模式的回答**逐字流式**出现；`extract` 模式渲染出字段表且可折叠查看原始 JSON。
3. 传一张**改了扩展名的图**（如把 `.gif` 改名成 `.png`），体检单应报 `mismatch` 并按真实格式处理。
4. 传一个**非图片文件**（如 `.txt`）或超 8 MB 的图，应看到明确的 400 提示，且**页面不崩**。
5. ⭐ 能讲清一句：**「让模型看图」改的到底是什么？**（答案：`messages` 里那条 user 消息的 `content` 结构。）
