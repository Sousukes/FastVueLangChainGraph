## 1. 阶段目标

阶段 07 结尾我们留下了一个"看起来能用"的 RAG：切块 → 嵌入 → 检索 → 生成。
它在一半的问题上表现不错，但另外一半会**悄悄答错**——而且不报错。

这一阶段从阶段 07 实测暴露的**两个真实失败**出发：

| 失败 | 现象 | 真正的病因 |
|---|---|---|
| 「MCP 有哪三条铁律？」 | 标准答案块在 333 块里**排第 25 名**，`top_k` 开到 8 都捞不到 | 答案只占块的一小部分，**块的向量被别的内​​容主导** |
| 「第 09 到第 15 阶段是主线还是能力插件？」 | TOP 1 落在含第 17/18 行的那一块 | 阶段总表被**切成表格碎片**，切块完全不懂结构 |

学完这一阶段，你会：

- 说清 **BM25** 的四样东西各在回答什么问题，以及它为什么"不懂语义却极其可靠"；
- 明白**中文为什么必须先分词**，并用 jieba 亲眼看到分词结果；
- 理解**为什么 BM25 分数和余弦相似度不能相加**，以及 **RRF** 是怎么绕开这个问题的；
- 说清 **bi-encoder（嵌入模型）和 cross-encoder（重排模型）的区别**，
  以及为什么**重排必须放在召回之后**；
- 知道"模型太大"的第一反应应该是**量化**（本项目把 1.06 GB 压到 266 MB）；
- 在前端看到一张**排名对照表**：同一个块在向量 / BM25 / 融合 / 重排各阶段的名次。

> **这一阶段真正要建立的直觉**：RAG 的检索不是"一个函数"，而是一条**管道**。
> 管道里每一段都有自己的偏见——向量偏语义、BM25 偏字面、重排偏"整体相关性"。
> **把它们串起来，不是因为哪个更好，而是因为它们会犯不同的错。**

## 3. 核心概念

### 3.1 先复习：阶段 07 到底错在哪

把阶段 07 的失败摊开看，会发现它们**不是同一个病**：

```
「MCP 有哪三条铁律？」
    向量检索认为：讲"第三条铁律"的块最像（0.4974）
    但真正的答案块（三条铁律齐全那句）排第 25 名
    → 病因：答案只占块的一小部分，块的向量被其他内容主导
    → 属于「没捞到」

「第 09 到第 15 阶段是主线还是能力插件？」
    向量检索把含第 17/18 行的块排在含第 09–15 行的块前面
    → 病因：阶段总表被切成 4 块表格碎片，切块不懂结构
    → 属于「捞错了」
```

**两个病，需要两种药。** 这一阶段给三种：

| 药 | 治什么 | 原理 |
|---|---|---|
| **BM25**（关键词召回） | 精确术语捞不到 | 完全不懂语义，只数词——**"字面命中"这件事它极其可靠** |
| **RRF**（融合） | 两路排名不一致 | 只看名次不看分数，把两路"共识"的块顶上来 |
| **重排**（Cross-encoder） | 前两路都不够准 | 让模型**把问题和候选拼在一起读一遍**，真正判断相关性 |

### 3.2 关键词检索：BM25

BM25 是 1994 年的算法，比深度学习早了二十年，但**今天依然是几乎所有搜索引擎的第一层**。
它的公式看起来吓人，其实每一项都在回答一个朴素的问题：

```
score(q, d) = Σ_{t∈q}  IDF(t) ·  f(t,d)·(k₁+1)
                                  ─────────────────────────────
                                  f(t,d) + k₁·(1-b+b·|d|/avgdl)
```

| 项 | 它在问什么 | 直觉 |
|---|---|---|
| `f(t,d)` | 词 t 在文档 d 里出现了几次？ | 出现越多越相关 |
| `IDF(t)` | 词 t 在全库里有多稀有？ | "的"出现在每篇文档里，它什么也说明不了；"铁律"很稀有，它一出现就很有信息量 |
| `\|d\| / avgdl` | 这篇文档比平均长多少？ | 长文档天然容易撞词，要**压一压** |
| `k₁`、`b` | 两个旋钮 | `k₁` 控制词频的饱和速度，`b` 控制长度惩罚的力度 |

**"饱和"是 BM25 最精妙的一处。** 词频的作用不是线性的：

```
出现 1 次 → 2 次      意义重大（从"提了一下"变成"重点讲了"）
出现 20 次 → 21 次    几乎没区别
```

所以公式里 `f` **在分母也出现了一次**——出现次数再多，分数也会被压在一个上限附近。
经典默认值是 `k₁ = 1.5`、`b = 0.75`，几乎所有实现都用这两个数。

**IDF 为什么加 1？** 朴素公式是 `ln((N - n_t + 0.5) / (n_t + 0.5))`。
如果一个词在**每一块**里都出现（`n_t = N`），这个式子会得到**负数**——反而倒扣分，
那显然不合理。加 1 就把它拉回非负区间。

> **BM25 有一个你必须知道的"缺陷"**：它**没有"不相关"的概念**。
> 只要查询里有词在库里出现过，它就一定会返回 top-k 个结果，而且分数看起来"很高"。
> 实测：问「今天北京的天气怎么样」，BM25 给 `07-RAG基础#11` 打了 **9.21 分**（看着挺高），
> 但那块只是在讲"天气"这个例子。**BM25 的分数只有相对意义，没有绝对阈值。**

### 3.3 中文为什么要先分词

英文用空格天然分词，`split()` 就够了。中文不行：

```
"三条铁律"  如果整段当一个词 → 用户搜"铁律"永远匹配不上
```

所以中文关键词检索的**地基是分词**。jieba 的实际输出（本项目实测）：

```python
tokenize("MCP 有哪三条铁律？")        → ['mcp', '哪', '三条', '铁律']
tokenize("isError 不是协议错误")      → ['iserror', '不是', '协议', '错误']
tokenize("RAG 的切块大小和重叠是怎么设置的？") → ['rag', '切块', '大小', '重叠', '设置']
```

三件事值得注意：

1. **`MCP`、`RAG`、`isError` 被转成小写**——这样 `isError` / `iserror` / `IsError` 都能命中；
2. **"三条"和"铁律"被切开了**——所以搜"铁律"能命中，这正是我们要的；
3. **停用词被去掉了**——"的""是""怎么"这类词几乎不携带区分度，
   留着只会让每块都"命中"，反而稀释了真正有信息量的词。

> **不要把否定词放进停用词表。** "不需要 Key" 和 "需要 Key" 是两回事。
> 停用词表图省事抄一份通用的，很容易把"不""没""无"顺手删掉——**然后语义就反了**。

### 3.4 融合：为什么不能把分数相加

有了两路召回，最自然的想法是"把分数加起来"。**这一步会毁掉一切**：

```
余弦相似度：0.8144、0.6753、0.6560       差距在 0.0x 量级
BM25 分数： 24.89、18.23、12.27          差距在 1~10 量级
```

两者的**量纲完全不同**。直接相加，BM25 会彻底压死向量——**这不是"融合"，是"覆盖"**。
而且这不是调个系数就能解决的问题：BM25 的分数范围**随语料变化**，
今天最大 25，换一批文档可能最大 250。

### 3.5 RRF：只看名次

**RRF（Reciprocal Rank Fusion）** 绕开了整个量纲问题——**它只看名次，不看分数**：

```
score(d) = Σ_i  1 / (k + rank_i(d))
```

一个块在向量里排第 1、在 BM25 里排第 3，它的得分就是 `1/61 + 1/63 ≈ 0.0323`。
**两路都靠前的块自然浮上来**——这正是"融合"想要的效果。

`k = 60` 是论文里的经验值。它的含义是**削弱头名的绝对优势**：
如果 `k = 0`，第 1 名的得分是 1、第 2 名是 0.5，差距 2 倍；
有了 `k = 60`，第 1 名是 `1/61`、第 2 名是 `1/62`，差距只有 1.6%。
**"第 1 名和第 2 名的差距，不应该比第 20 名和第 21 名的差距大 20 倍。"**

> **RRF 的代价也要说清楚**：它**只奖励"共识"**。
> 一个块如果只被一路召回（比如只有 BM25 找到了它），它的 RRF 得分天然就低——
> 哪怕它正是答案。本项目实测就撞上了这个：
>
> ```
> 「MCP 有哪三条铁律？」  目标块 06-MCP协议开发#29
>     向量：未进前 10        BM25：第 1 名（10.446）        RRF 融合：第 4 名
> ```
>
> **BM25 明明把它排第 1，融合后却掉到第 4。** 因为向量那一​​路"没投它的票"。
> 这正是为什么**光有融合还不够，还得有重排**。

### 3.6 重排：让模型真正读一遍

到目前为上，两路召回都是**双塔（bi-encoder）**结构：

```
bi-encoder：  问题 ──→ [编码器] ──→ 向量 ┐
                                          ├─ 算距离
              文档 ──→ [编码器] ──→ 向量 ┘

cross-encoder： (问题, 文档) ──→ [编码器] ──→ 一个分数
```

差别在哪？

- **bi-encoder**：问题和文档**各自**编码，**它们从没见过面**。快到可以预先算好所有文档向量
  （这正是向量库存在的意义），但"问题里这个词和文档里那句话到底对不对得上"这件事，
  模型只能靠向量的整体方向去猜。
- **cross-encoder**：把 **(问题, 文档) 拼成一条序列**一起送进模型，
  注意力可以在两者之间**自由流动**。判断准得多，但**每一对都要跑一次前向**——
  333 块全跑一遍是慢的，而且新增文档要全部重算。

**所以标准做法是两段式**：

```
bi-encoder 粗筛出几十条  →  cross-encoder 精排  →  取 top-3
   （快，但糙）                （慢，但准）
```

**这就是为什么重排必须放在召回之后**，也是为什么候选数不能太大——
重排的开销和候选数成正比。

### 3.7 更新版：三种失败模式与三种修法

阶段 07 那张表可以升级了：

| 现象 | 病因 | 修法 | 本阶段用的 |
|---|---|---|---|
| 精确术语答不上 | 向量把术语和近义表达混在一起 | **加关键词召回** | ✅ BM25 |
| 两路结果不一致、不知道该信谁 | 单路有偏见 | **融合** | ✅ RRF |
| 前两路都排不对 | 两者都没真正"读"内容 | **重排** | ✅ Cross-encoder |
| 捞对了但模型不用 | 生成没听话 | 改 system prompt、减 `top_k` | 阶段 07 已解决 |
| 库里确实没有 | 语料问题 | 加文档 | — |

> **顺序很重要**：先看「检索捞回了什么」，再看「重排有没有排对」，最后才看「模型有没有用好」。
> 前端那张对照表就是为这个顺序服务的。

## 4. 动手实现

### 4.1 后端 · 分词与 BM25：`bm25.py`

```python
K1 = 1.5      # 词频饱和速度
B = 0.75      # 长度惩罚力度

def tokenize(text: str) -> list[str]:
    """中文分词 → 归一化 → 去停用词。"""
    out = []
    for word in jieba.cut(text):
        w = word.strip().lower()
        if not w or w in STOPWORDS or not _is_content(w):
            continue
        out.append(w)
    return out
```

BM25 索引本体是一个朴素的"全量装内存"实现：

```python
class BM25Index:
    def build(self, texts):
        self.tf = [Counter(tokenize(t)) for t in texts]   # 每块的词频
        self.n = len(self.tf)
        self.doc_len = [sum(c.values()) for c in self.tf]
        self.avgdl = sum(self.doc_len) / self.n
        self.df = Counter()
        for counter in self.tf:
            self.df.update(counter.keys())                # 每块只计一次 → 就是 df

    def idf(self, term):
        n_t = self.df.get(term, 0)
        return math.log(1 + (self.n - n_t + 0.5) / (n_t + 0.5))   # 加 1 保证非负

    def score(self, query_tokens, doc_id):
        tf, dl = self.tf[doc_id], self.doc_len[doc_id]
        total = 0.0
        for term in query_tokens:
            f = tf.get(term, 0)
            if not f:          # ← 没出现的词直接跳过，这就是"字面匹配"
                continue
            norm = 1 - self.b + self.b * dl / self.avgdl
            total += self.idf(term) * (f * (self.k1 + 1)) / (f + self.k1 * norm)
        return total
```

**为什么不用 Elasticsearch？** 因为本项目只有几百块，全量装内存、每次线性打分
**实测 < 5 ms**，完全够用。真实生产环境会换成倒排索引，但**打分公式是一模一样的**——
先把公式搞懂，再去用现成的。

### 4.2 后端 · RRF 融合：`bm25.py`

```python
def rrf_fuse(rankings: list[list[int]], k: int = 60) -> list[tuple[int, float]]:
    acc = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            acc[doc_id] = acc.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(acc.items(), key=lambda p: (-p[1], p[0]))
```

**九行。** 融合这件事的复杂度全在"想清楚"上，不在代码量上。

### 4.3 后端 · 重排：`rag.py`

```python
RERANK_MODEL = "Xenova/bge-reranker-base"
RERANK_MODEL_FILE = "onnx/model_quantized.onnx"     # ← 关键是这一行

def get_reranker() -> TextCrossEncoder:
    global _reranker
    if _reranker is None:
        registered = {m["model"] for m in TextCrossEncoder.list_supported_models()}
        if RERANK_MODEL not in registered:
            TextCrossEncoder.add_custom_model(
                model=RERANK_MODEL,
                sources=ModelSource(hf=RERANK_MODEL),
                model_file=RERANK_MODEL_FILE,        # 指向量化版
                size_in_gb=0.26,
            )
        _reranker = TextCrossEncoder(model_name=RERANK_MODEL)
    return _reranker
```

内置源指向 fp32（1.06 GB），我们**注册一个自定义模型把 `model_file` 指到量化版**——
这是 FastEmbed 提供的扩展点，也是"量化优先"这个思路的落地。

再配一个"只查缓存、不触发下载"的状态函数：

```python
def rerank_ready() -> bool:
    """重排模型是否已在本地（只查缓存，不触发下载）。"""
    cached = try_to_load_from_cache(RERANK_MODEL, RERANK_MODEL_FILE,
                                   cache_dir=str(define_cache_dir()))
    return isinstance(cached, str) and Path(cached).exists()
```

> **为什么要把这个 boolean 暴露出去？** 因为"要下 266MB"这件事
> **不该是用户点完之后才发现的意外**。前端的提示条就是靠它。

### 4.4 后端 · 管道与排名对照表：`rag.py`

`hybrid_search()` 是本阶段的核心。它的返回值不只是结果，还有**一张排名对照表**：

```python
def hybrid_search(query, top_k=3, mode="hybrid", rerank=False, candidates=10) -> dict:
    rows = corpus()                       # 统一语料视图（向量和 BM25 共享同一套块编号）

    vec = vector_ranking(query, candidates)          # ① 向量召回
    bm  = bm25_ranking(query, candidates)            # ② BM25 召回

    if mode == "vector":   fused = vec
    elif mode == "bm25":   fused = bm
    else:                  fused = rrf_fuse([[i for i, _ in vec], [i for i, _ in bm]])

    if rerank:                                       # ③ 重排（只对融合后的候选池）
        pool = [i for i, _ in fused][:max(candidates, top_k)]
        scores = rerank_scores(query, [rows[i]["text"] for i in pool])
        reranked = sorted(zip(pool, scores), key=lambda p: (-p[1], p[0]))

    final = reranked or fused
    ...
```

**两个设计决定值得单独说：**

**① 为什么要一个 `corpus()`？**
向量检索和 BM25 是两套完全不同的打分机制，要融合就必须先让两边
**指向同一批"块"**。这里把库里的块整体取出来，用**列表下标**当块的内部编号。
顺带一个坑：**语料一变，这个缓存和 BM25 索引都要失效**，
否则检索结果会"慢半拍"——刚导入的文档怎么搜都搜不到。所以入库 / 删除 / 清空三处都要记得调 `invalidate_cache()`。

**② 为什么返回 `rows` 而不只是 `hits`？**
因为本阶段要教的不是"结果是这些"，而是**"结果是怎么来的"**。
`rows` 里每一行带着同一个块在四个阶段的名次和分数：

```python
{
  "title": "06-MCP协议开发", "index": 29,
  "vector_rank": None, "bm25_rank": 1, "fused_rank": 4, "rerank_rank": ...,
  "vector_score": None, "bm25_score": 10.446, "fused_score": ..., "rerank_score": ...,
  "in_final": True,
}
```

前端拿它直接渲染成一张表，**不需要任何额外解释**。

### 4.5 后端 · 路由：`main.py`

`/api/rag/search` 和 `/api/rag/ask` 各多了三个**带默认值**的参数：

```python
mode: Literal["vector", "bm25", "hybrid"] = "vector"   # 默认仍是纯向量

原因很直白：**重排只能重排"已经召回到的块"**。向量召回的前 10 名里根本没有

> **这是本阶段最容易搞反的一件事**：很多人以为"加了重排就等于检索变准了"。
> 不对——**召回负责"不漏"，重排负责"排对"**。
> 召回漏掉的，重排一个也救不回来。
> 所以顺序永远是：**先用混合召回把面铺开（宁可多捞），再让重排去精排。**
> 把重排当成"补救召回缺陷的银弹"，是最常见的误用。

## 6. 小结

- **RAG 的检索是一条管道，不是一个函数。** 向量偏语义、BM25 偏字面、重排偏整体相关性——
  把它们串起来，不是因为哪个更好，而是因为**它们会犯不同的错**。
- **BM25** 的公式只有四个部件：词频 `f`、稀有度 `IDF`、长度归一 `|d|/avgdl`、两个旋钮 `k₁`/`b`。
  它的"饱和"设计（`f` 同时出现在分母）是精髓。
- **中文必须先分词**，否则"铁律"这种词永远匹配不上。**停用词表里千万别放否定词。**
- **BM25 没有"不相关"的概念**——它总会返回 top-k，分数只有相对意义，没有绝对阈值。
- **分数不能相加**：余弦是 0~1、BM25 是 0~几十，量纲不同。**RRF 只看名次，绕开了这个问题。**
- **RRF 只奖励共识**：只被一路召回的块，得分天然低——**这是实测撞出来的坑，也是需要重排的原因**。
- **bi-encoder 粗筛 → cross-encoder 精排**是标准两段式。重排慢，所以**必须放在召回之后**，
  而且候选数不能太大。
- ⭐ **召回负责"不漏"，重排负责"排对"——这是本阶段最容易搞反的一件事。**
  重排只能重排**已经召回到的块**；召回漏掉的，重排一个也救不回来（实测：切回「向量」模式时
  ★ 行整行消失）。所以顺序永远是：**先用混合召回把面铺开（宁可多捞），再让重排去精排**。
  把重排当"补救召回缺陷的银弹"，是最常见的误用。
- **重排是管道里唯一一个线性成本的环节**（实测约 63 ms/候选：5→310ms、50→3565ms）。
  其余三步是常数或对数级——这就是候选数不能给大的量化依据。
- **cross-encoder 输出的是原始 logit，可以是负数**（实测相关 8.165 / 不相关 −10.178）。
  它不是 0~1 的相似度，**不能当阈值，更不能参与 RRF 融合**（量纲又不一样了）。
- **"模型太大"先想量化**：本项目把 1.06 GB 的 fp32 重排模型换成了 266MB 的 int8 版。
- **默认值保持向后兼容**：`mode` 默认 `"vector"`，所以阶段 07 的页面照旧工作，
  而且顺便成了本阶段的对照组。
- **懒加载是有代价的**：冷启动首次检索实测约 **4.7 s**（嵌入模型 + jieba 词典 + 重排模型
  三份加载费一次性付清）。生产环境应在服务启动时预热。

1. 把 `rrf_fuse` 改成接受 `[(ranking, weight), ...]`，得分改成 `Σ w_i / (k + rank_i(d))`；
2. `weight` 用 `float`（0~1）表示"向量那一路的权重"，BM25 自动取 `1 - weight`；
3. 加进 `RagSearchRequest`，前端加一个滑块；
4. 验证：在「MCP 有哪三条铁律？」上，把向量权重调到 0.2，
   观察 ★ 行的融合名次怎么变——**从第 4 往第 1 靠**。

**验收标准**

1. `weight=0.5` 时结果与现在的等权 RRF **完全一致**（这是回归基线）；
2. `weight=0` 时结果与 `mode="bm25"` 的排序一致；`weight=1` 时与 `mode="vector"` 一致；
3. 能说清：**为什么等权未必是最优的**，以及"调权重"和"加重排"各自的代价是什么；
4. 前端滑块拖动后，对照表实时更新，且 ★ 行的名次变化可见。
