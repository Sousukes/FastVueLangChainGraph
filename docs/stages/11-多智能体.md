# 阶段 11 · 多智能体（Multi-agent）

> 阶段 10 的 ReAct 是「一个全才」：一个智能体、一套工具、一个循环、一个提示词。
> 本阶段把它拆成**几个专职角色**，由一个编排器（orchestrator）串起来：
>
> ```
> 用户问题 → Planner 拆解 → 各角色并行执行 → Critic 评审 → Writer 汇总
> ```
>
> 但请先接受一个反直觉的结论：**多智能体并不比单智能体「更聪明」，它只是「更可控、更可观测」**。
> 代价是**耗时按角色数线性增长**（本地实测：单智能体 ~3.4s → 多智能体 ~8–22s）。
> 所以本阶段真正要回答的问题不是「怎么搭多智能体」，而是
> **「什么时候值得多付这几倍的时间」**。

---

## 1. 阶段目标

阶段 10 把「一个全才」做扎实了，但它有一个绕不开的短板：**一个循环里既要查资料、又要算、又要行文，提示词会越写越长，模型也越容易顾此失彼**。

多智能体给出的不是「更聪明」，而是三件**可控性**上的事：

| 想要什么 | 单智能体（阶段 10） | 多智能体（本阶段） |
|---|---|---|
| **专人专岗** | 一个提示词啥都管 | 研究员只查、分析员只算、评审员只挑刺 |
| **可观测** | 只能看一条长 trace | 每个角色一份独立时间线 + 各自的工具面 |
| **可重试** | 一步错整段重来 | 单个 worker 失败可单独重跑 |

本阶段要做的三件事：

```
① 角色分工   每个角色一套不同的工具面（researcher 能检索、analyst 能计算、critic 没有工具）
② 编排器     Planner 拆任务 → 拓扑分层并行 → Critic 评审 → Writer 汇总
③ 结构化交接 角色之间只传「结论 + 证据」，不传完整对话历史
```

学完你应该能回答：

- 为什么「多个角色」不等于「多智能体」？什么叫**伪多智能体**？
- 并行一定更快吗？用 §5 的实测数据说明为什么这次**并行反而更慢**。
- 角色之间为什么要只传「结论 + 证据」，不传完整对话？
- Critic 为什么自己也会幻觉？怎么防止它「听它自己说自己是对的」？
- 多智能体的成本怎么算？**什么时候该用回单智能体**？

## 3. 核心概念

### 3.1 多智能体解决的是「可控性」，不是「智力」

一句话：**同一个模型，分到 N 个角色里，不会凭空变聪明**。它变好是因为：

- 每个角色的提示词更窄，模型更不容易跑偏；
- 出错时能定位到「哪个角色」而不是「那一长串里的某一行」；
- 你可以给每个角色不同的 `temperature`（规划员 0.1、主笔 0.3）。

记住这点，就能避开多智能体最常见的两个坑：**为用而用**、**以为分了角色就变强了**。

### 3.2 分工要真实生效，必须同时做到三件事（缺一件就是伪多智能体）

⭐ **这是本阶段最重要的一个判断**。

```
1. 工具面不同   researcher 只能检索、analyst 只能计算、critic 没有工具。
               ↑ 如果所有角色拿同一套工具，它们会退化成「同一个智能体跑 N 遍」——
                 角色名写得很漂亮，实际什么也没分。这是多智能体最常见的自欺。
2. 上下文不共享 角色之间只传「结论 + 证据」，不传彼此的完整对话。
               ↑ 否则上下文按角色数线性膨胀（每多一个角色就多一份完整历史）。
3. 交接结构化   Planner 和 Critic 的输出走 JSON + Pydantic 校验，不是让模型自由发挥一段话。
               ↑ 否则下游要拿正则去抠，一个格式漂就全崩。
```

后文 §4 的 `run_team` 就是这三件事的代码落地。`GET /api/team/roles` 会把每个角色的**工具面**摊开给前端——两个角色 tools 一模一样，就是伪多智能体，一眼能看出来。

### 3.3 并行性的唯一来源：依赖分层

多智能体唯一的速度红利来自**同层任务并行**。调度器按 `dependsOn` 做拓扑分层：同层无依赖 → 并行；有依赖 → 等前一层。

```python
# backend/team.py —— _layers()
def _layers(tasks):
    remaining = list(tasks)
    done = set()
    out = []
    while remaining:
        layer = [t for t in remaining if all(d in done for d in t.dependsOn)]
        if not layer:
            break                       # 剩下的全部依赖不到 → 丢弃（避免死循环）
        out.append(layer)
        done.update(t.id for t in layer)
        remaining = [t for t in remaining if t.id not in done]
    return out
```

⚠️ 两个真实约束：

- **循环依赖会被直接丢弃**（t1 依赖 t2、t2 依赖 t1）。这里不做环检测——约束交给 Planner 的提示词更划算。
- **如果所有任务都写满 `dependsOn`，分层退化成一条链**，多智能体的耗时 = 单智能体 × 角色数，而且**一点并行红利都没有**。所以 Planner 的提示词专门强调：「能并行的别写成串行」。

### 3.4 交接只传「结论 + 证据」，而且 evidence 必须是调用记录

角色之间传什么，决定了 Critic 能不能正常工作。两件事必须分开：

> **结论是主张，调用记录才是证据。** 否则评审员等于「听它自己说自己是对的」。

```python
# backend/team.py —— _feed_evidence()
# ⚠️ 不能从 trace 里取 observation：阶段 10 的 trace 只记了 {tool, arguments, ok, ms}，
#    没保存 observation 原文（观测当年只作为 SSE 事件发出）。如果照着 trace 读
#    act["observation"]，拿到的是空字符串 → 评审员看不到任何证据 → 把每条结论都判成
#    "无支撑"。一个静默失效的审查，比没有这个角色更糟（它还让你以为审查过了）。
#    所以这里按 callId 把 action 和 observation 事件配成对。
def _feed_evidence(buf, ev):
    if ev.get("type") == "action":
        buf.append({"callId": ev.get("callId"), "tool": ev.get("tool"),
                    "arguments": ev.get("arguments"), "observation": ""})
    elif ev.get("type") == "observation":
        for item in buf:
            if item.get("callId") == ev.get("callId"):
                item["observation"] = (ev.get("content") or "")[:_EVIDENCE_LIMIT]
                return
```

`_handoff()` 打包时只带 `conclusion`（结论文本截断到 700 字）+ `evidence`（调用记录，每条 300 字）。**不给完整对话历史**——这正是 §3.2 第 2 条「上下文不共享」的代码落地。

### 3.5 成本线性增长 —— 何时不该用多智能体

本阶段的硬账：**多智能体的耗时 ≈ 单智能体 ×（角色数对应的 LLM 调用数）**。理由很简单——Planner 一次、每个 worker 一次、Critic 一次、Writer 一次，全是独立 LLM 调用，叠加起来。

本地实测（`deepseek-flash`，一次具体运行，LLM 延迟有抖动，但量级稳定）：

| 方案 | 问题：「分别算 (400+200)\*2 和 360/12，再加总」 | 倍数 |
|---|---|---|
| 单智能体 `run_react_blocking` | **3.41 s** | 1× |
| 多智能体 `parallel=False`（串行） | **7.92 s** | ×2.32 |
| 多智能体 `parallel=True`（并行） | **22.17 s** | ×6.51 |

把多智能体那次拆开看成本（单位 s）：

```
并行：plan 6.86 | work 4.80 | review 9.34 | write 1.17  → 总 22.17
串行：plan 1.56 | work 3.17 | review 1.67 | write 1.52  → 总  7.92
```

**注意一个反直觉的结果：这次并行比串行还慢（22s vs 8s）。** 原因有两层，都值得记住：

1. **固定串行开销吞掉了并行红利。** Planner + Critic 两次 LLM 调用，无论并行与否都要付；本例 Critic 单次就 1.7–9.3s。worker 那点重叠收益（t1、t2 重叠）被这块固定开销盖过了。
2. **本地并行 ≠ 远端更快。** 两个 worker 同时打 DeepSeek，触发了并发排队/延迟抖动，导致并行时每个请求反而比串行时更慢。worker 越「轻」（只一两次短调用），越容易被这块抖动反噬。

> **结论（也是本阶段的核心论点）**：多智能体的「快」只在 **worker 重（多次检索 / 长推理）且远端不限流** 时才兑现。否则——尤其当问题本身一个角色就能解决时——**老老实实用单智能体**，又快又便宜又不容易出幺蛾子。

### 3.6 Critic 自己也会幻觉

评审员没有工具，只能就手上的材料论材料。这带来一个陷阱：

> 如果 `evidence` 是空的（§3.4 那种静默失效），Critic 会**看不到任何证据**，于是把每条结论都判成「无支撑」——它以为自己在严格审查，其实在瞎判。

反过来，如果证据充分，Critic 也必须**判 pass**，不能为了显得严格而挑刺。所以 `CRITIC_SYSTEM` 里专门写了两条：

```
⚠️ 不要为了显得严格而挑刺：证据充分就判 pass。
⚠️ 也不要脑补证据：你没看到的就是没看到，不能因为「它大概对」就放过。
```

Writer（`WRITER_SYSTEM`）也要对 Critic 的判定负责：**被标记无证据的结论，要么补一句「此点缺少检索支撑」，要么直接不用**——不能原样写进答案，那等于把幻觉洗白成正文。

## 4. 动手实现

### 4.1 角色定义：分工的实质在 `groups`

角色用 `@dataclass` 描述，`groups` 才是分工的实质（`system` 只是让它更愿意用对工具）：

```python
# backend/team.py
@dataclass(frozen=True)
class Role:
    name: str
    label: str
    system: str
    groups: tuple[str, ...]      # ⭐ 工具面，分工的实质
    max_steps: int = 1
    temperature: float = 0.2

ROLES = {
    "planner":   Role(..., groups=(),           max_steps=1, temperature=0.1),  # 无工具
    "researcher":Role(..., groups=(GROUP_RAG, GROUP_GRAPH), max_steps=3, temperature=0.2),  # 只能检索
    "analyst":   Role(..., groups=(GROUP_LOCAL,),        max_steps=3, temperature=0.1),  # 只能计算
    "critic":    Role(..., groups=(),           max_steps=1, temperature=0.1),  # 无工具
    "writer":    Role(..., groups=(),           max_steps=1, temperature=0.3),  # 无工具
}
```

`KIND_ROLE = {"research": "researcher", "compute": "analyst"}` —— 这就是「分工落地」的那一行：Planner 拆出的任务种类，在这里映射到具体角色。

### 4.2 编排主流程 `run_team`：逐事件 yield

`run_team(client, question, parallel=True)` 直接复用阶段 10 的 `run_react`，但每个 worker 换上自己的 `system` 和 `groups`。事件类型和阶段 10 基本一致，多了 `agent` 字段——**并行时必须有它，否则前端无法把交织的事件分回各自的角色**：

```
start / phase / plan / agent_start / delta / action / observation
/ agent_end / review / write / finish / error
```

关键片段（规划 → 分层 → 派工）：

```python
plan, _ = _chat_json(client, [...planner...], model, planner.temperature, PlanModel, PLAN_SCHEMA_HINT)
tasks = plan.tasks[:max_tasks]
for layer_no, layer in enumerate(_layers(tasks), start=1):
    ready = [(t, [h for h in handoffs if h["id"] in t.dependsOn]) for t in layer]
    yield {"type": "layer", "layer": layer_no, "parallel": parallel and len(ready) > 1, ...}
    for task, _ in ready:                      # 先把每个角色的工具面报出来
        role = ROLES[KIND_ROLE.get(task.kind, ROLE_RESEARCHER)]
        yield {"type": "agent_start", "agent": task.id, "role": role.name,
               "tools": [s["function"]["name"] for s in react.build_schemas(role.groups)], ...}
    # 同层 ≥2 个任务且 parallel=True → 走线程+队列；否则直接 for
    ...
```

### 4.3 Planner 与 Critic 的 JSON 自纠

两个「交接点」走 `client.chat(response_format={"type":"json_object"})` + Pydantic 校验 + **一次自纠重试**（沿用阶段 04 的思路）：

```python
def _chat_json(client, messages, model, temperature, validator, schema_hint):
    raw = client.chat(messages, model=model, temperature=temperature,
                      response_format={"type": "json_object"})
    for attempt in (1, 2):
        try:
            return validator.model_validate_json(_strip_fence(raw)), raw
        except (ValidationError, json.JSONDecodeError) as e:
            if attempt == 2:
                return None, raw               # 自纠失败 → 如实上报，不退化
            raw = client.chat(messages + [自纠提示], model=model, temperature=temperature)
```

⭐ 为什么必须自己收口成结构化对象：多智能体的交接点一多，任何一个「模型自由发挥了一段话」的环节都会变成下游的解析泥潭。**角色之间的接口要像函数签名一样硬。**

### 4.4 并行调度：线程 + 队列 + 哨兵

阶段 10 说过「能自己拆开的流程就别用线程去绕」。本阶段**恰恰相反**——多个 worker 天然是同时跑的独立流程，谁先产出一帧不确定，必须回到「后台线程 + `queue.Queue` + 哨兵」（阶段 09 那一套）。**判据是「流程本身是否并发」，不是「能不能用生成器拆开」。**

```python
if parallel and len(ready) > 1:
    q: "queue.Queue[tuple[str, dict | None]]" = queue.Queue()
    def worker_body(task, deps):
        try:
            for ev in react.run_react(client, _worker_prompt(task, deps),
                                       model=model, max_steps=role.max_steps,
                                       temperature=role.temperature, groups=role.groups,
                                       system=role.system, observation_limit=observation_limit):
                q.put((task.id, ev))
        except Exception as e:
            q.put((task.id, {"type": "error", "message": f"{task.id} 执行失败：{e}"}))
        finally:
            q.put((task.id, _SENTINEL))        # 哨兵：这个 worker 跑完了
    with ThreadPoolExecutor(max_workers=len(ready)) as ex:
        for task, deps in ready:
            ex.submit(worker_body, task, deps)
        finished = 0
        while finished < len(ready):
            tid, ev = q.get()
            if ev is None:                      # 哨兵
                finished += 1; yield {"type": "agent_end", "task": tid}; continue
            _feed_evidence(evidence[tid], ev)   # 顺手收集证据
            ev = _normalize_worker_event(ev)
            if ev is None: continue
            yield {**ev, "agent": tid}         # 补上 agent 字段，供前端分列
            if ev.get("type") == "agent_result":
                layer_results[tid] = ev["result"]
```

`_normalize_worker_event` 把 worker 的 `finish` 改名为 `agent_result`——否则前端分不清「某个角色跑完了」和「整个团队跑完了」（两者原本都叫 `finish`）。

### 4.5 后端路由与前端

后端补三个端点（`backend/main.py`）：

```python
@app.get("/api/team/roles")                       # 角色工具面清单（前端自检伪多智能体）
@app.post("/api/team/run")                         # 非流式，收口成完整结果
@app.post("/api/team/stream")                      # SSE，逐事件推送（带 agent 字段）
```

前端 `useTeam.ts` 是个 SSE 状态机：按 `agent` 把事件分进各角色的时间线列，同时维护「拓扑分层」视图。**它的核心交互是单智能体 vs 多智能体并排对比**——同一个问题跑两遍（`/api/agent/stream` 和 `/api/team/stream`），并排显示耗时 / 答案 / 证据，直接把 §3.5「什么时候不该用」讲清楚。`TeamConsole.vue` 渲染角色工具面、规划、分角色时间线、评审、汇总。

在 `/team` 页面选一个预设问题，点「运行多智能体」：能看到 Planner 拆出的任务、各角色的分层时间线、每角色的工具面、Critic 的 verdict、Writer 的流式汇总。点「单 vs 多并排」可同时跑单智能体对照，直观看到 §3.5 的耗时差距。

## 6. 小结与练习

**小结**：多智能体不是「更聪明的单智能体」，而是「更可控、更可观测的单智能体集合」。它成立的三个前提是——**工具面不同**（否则伪多智能体）、**只传结论+证据**（否则上下文膨胀且 Critic 失明）、**交接结构化**（否则下游解析崩）。它的代价是**成本按角色数线性增长**，并行只在 worker 重且远端不限流时才省钱；否则老老实实用单智能体。

**练习**：

1. 把 `ROLES["researcher"].groups` 改成和 `analyst` 一样，再打开 `/team`——前端角色工具面清单会变成两个角色 tools 相同，这就是「伪多智能体」的直观样子。改回去。
2. 在 `PLANNER_SYSTEM` 里把「能并行的别写成串行」删掉，观察 Planner 是否更倾向于把所有任务写成 `dependsOn` 链，并行红利如何消失。
3. 给 `run_team` 传 `parallel=False`，对比 §5.2 的耗时——想清楚为什么本例串行反而更快。
4. 故意在 `_feed_evidence` 里把 `observation` 赋值那行注释掉，跑 `_t_team_research.py`——看 Critic 的 verdict 如何从 issue 退化成「每条都无支撑」，体会 §3.6 说的「静默失效的审查」。

**验收**：`backend/_t_team_static.py` 全绿；`/team` 页面能跑通一个含 research + compute 的问题，且首页「已发布阶段」已补登阶段 11。
