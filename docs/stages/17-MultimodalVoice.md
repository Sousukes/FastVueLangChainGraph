# 阶段 17 · 多模态·语音

> 阶段 16 把**图片**变成了输入，本阶段处理另一种模态：**声音**。
> 但在写第一行代码之前，必须先问一个**工程边界**问题——**语音能力到底归谁？**
>
> 我是先动手测的，不是先猜的：
>
> ```
> POST /audio/transcriptions   →  404
> POST /audio/speech           →  404
> ```
>
> **DeepSeek 没有音频接口。** 这个事实唯一地决定了本阶段的设计：
> 音频的采集与播放留在**浏览器**（Web Speech API，零依赖零密钥），
> 服务端只做它真正该做的两件事——把书面语改写成**念得顺**的口语、
> 把符号改写成**读出来的样子**。
>
> 所以本阶段的重点不是「怎么调语音模型」，而是：
> **先想清楚边界，再写代码。**

## 1. 阶段目标

- 学会在动手前先做**边界判断**：一项能力该放客户端还是服务端？判据不是「哪边写起来顺手」，而是**平台已经提供了什么**。
- 实测确认一个关键事实：**DeepSeek 只有文本接口**（`/audio/*` 全 404），因此音频边界必须落在浏览器。
- 掌握浏览器的 **Web Speech API**：`SpeechRecognition`（语音转写 ASR）+ `speechSynthesis`（语音合成 TTS），
  并理解为什么「能用平台能力解决的事就别自己造」。
- 掌握服务端**真正值得做的**两件事：
  1. **口语化改写**：书面语 → 适合朗读的短句，且**去干净 Markdown**（`## 标题`、`- 列表`、`**加粗**` 念出来全是噪声）；
  2. **朗读稿规范化**（Text Normalization，TTS 之前的真实环节）：`2026-09-21` → `二零二六年九月二十一日`、
     `¥2,158.50` → `两千一百五十八元五角`、`USB-C` → `U S B C`。
- 学会把「念得顺」这种主观要求**变成可断言的数字**：一条正则数出残留 Markdown 标记数。
- 把「模型自述」进一步**降级为可核对**：模型自己列的改写对照表，逐条核对它是否真的发生在文本里。
- 产出一个完整前端页面：麦克风拾音（含实时临时转写）→ 流式口语稿 → 朗读稿 + 浏览器朗读（语速/音色可调）→ 对照表与体检数字。

## 3. 核心概念

### 3.1 先问边界：语音能力归谁？

这是本阶段真正要教的东西。动手之前先测一件事——**平台有没有现成的语音接口**：

```python
c._client.audio.transcriptions.create(model="whisper-1", file=("a.wav", wav, "audio/wav"))  # → 404
c._client.audio.speech.create(model="tts-1", voice="alloy", input="你好")                    # → 404
```

两条都是 **404**。于是设计被这个事实**唯一地**决定了：

```
┌──────────── 浏览器（Web Speech API，零依赖零密钥）────────────┐
│  🎤 SpeechRecognition（ASR）──转写文本──▶                     │
│                              ◀──朗读稿── speechSynthesis（TTS）│
└───────────────────────────────────────────────────────────────┘
                              │            ▲
                         转写文本          朗读稿
                              ▼            │
┌──────────────────── 后端：语音管线的文本侧编排 ─────────────────┐
│  ① 口语化改写（LLM，**流式**）   书面语 → 适读短句，且无 Markdown │
│  ② 朗读稿规范化（LLM，JSON）     Text Normalization            │
│  ③ 确定性体检（**不用模型**）     残留 Markdown 数 + 朗读时长估算 │
└───────────────────────────────────────────────────────────────┘
```

**为什么音频边界要放在浏览器？** 把它硬搬到服务端，就得自己引入一套 ASR/TTS 服务与密钥——
收益为零、复杂度暴涨，而 Web Speech API 在 Chrome/Edge 上开箱即用。

| 判断 | 理由 |
|---|---|
| ASR/TTS 放浏览器 | 平台已提供，零依赖零密钥；音频不必离开用户的机器 |
| 口语化改写放服务端 | 需要 LLM，且**密钥只该存在服务端 `.env`**（阶段 03 定下的底线） |
| 文本规范化放服务端 | 需要 LLM 判断上下文（`2026-09` 是日期还是型号？） |
| Markdown 体检放服务端 | **不需要** LLM——一条正则，确定性 |

### 3.2 「能读出来」≠「读得好」：服务端为什么不可省

如果只让 TTS 念模型的原始输出，会遇到两个**必然**问题：

```
模型默认输出                          直接送进 TTS 会念成
────────────────────────────────────────────────────────────
## 报销流程                           井号 井号 报销流程
- 第一步：提交单据                      减号 第一步 冒号 提交单据
**注意**：金额 ¥2,158.50              注意 冒号 金额 人民币 二 逗号 一五八点五零
单号 BX-2026-0917                     B X 杠 二零二六 杠 零九一七（或者直接跳过）
```

两类问题，两种解法：

| 问题 | 解法 | 为什么值得一次 LLM 调用 |
|---|---|---|
| Markdown 标记变成噪声 | ① 口语化改写时**硬性禁止** Markdown | 模型天然爱输出结构化文本，必须显式约束 |
| 符号写法读错 | ② 朗读稿规范化 | 需要**上下文**：`2026-09` 是日期，`USB-C` 是型号，`3.5%` 是百分比 |

### 3.3 两类「可验证」：确定性体检 + 对自述的核对

本阶段最有价值的设计，是把两个「看起来只能靠感觉」的要求变成**可断言的数字**。

**第一类：确定性体检**（根本不用问模型）

```python
def markdown_left(text: str) -> int:
    """数一数这段文字里还剩多少 Markdown 标记。"""
    return len(_MD_LINE_RE.findall(text)) + len(_MD_INLINE_RE.findall(text))
```

「口语稿必须无 Markdown」这条要求，**不需要 LLM 判定**——一条正则就能把它变成数字。
配合时长估算（中文 ≈ 4.5 字/秒、英文 ≈ 2.5 词/秒），服务端能给出「这段念出来大约 23 秒」这种硬读数。

**第二类：对模型自述的核对**（`termCheck`）

规范化阶段会返回一张对照表 `terms`：

```json
[{"from": "BX-2026-0917", "to": "B X 二零二六 零九一七"}]
```

⚠️ 但**这张表是模型的自述，不是 diff**。实测就抓到了它的不可靠（见 §5）：

- 改写阶段**自己**就把 `2026-09-17` 写成了汉字 `二〇二六 〇九一七`；
- 于是规范化阶段「没什么可改的」，对照表里只剩 `BX → B X`；
- 而对照表的读者很可能因此以为「数字没有被改过」——**它漏报了**。

修法只要一句 `in` 判断，把「自述」降级成「可核对」：

```python
def audit_terms(answer: str, speak: str, terms: list[dict]) -> dict:
    """每条 from 要真的出现在口语稿里、to 要真的出现在朗读稿里。"""
    suspect = [t for t in terms
               if t["from"] not in answer or t["to"] not in speak]
    return {"total": len(terms), "verified": len(terms) - len(suspect), "suspect": suspect}
```

### 3.4 一条贯穿三个阶段的暗线：从「声称」到「核对」

这三步是同一个思想的递进——**别信模型的自我陈述，去做能做的核对**：

| 阶段 | 字段 | 核对什么 | 判据 |
|---|---|---|---|
| 14 | `grounded` | 模型**声称**引用了吗 | 答案里的 `[n]` 能否对上来源编号 |
| 15 | `faithful` | 那些声称**被资料支持**吗 | 一次额外 LLM 调用逐句核查（这里仍要用模型） |
| **17** | **`termCheck`** | 那些自述的改写**真的发生了**吗 | **`in` 判断——纯确定性，不用模型** |

差别在于**成本**：14 是解析，15 必须再花一次模型调用，17 又回到了零成本——
**只要把问题问对，核对往往不需要模型。**

## 4. 动手实现

### 4.1 后端 `voice.py`：两阶段 + 确定性体检

事件协议延续阶段 10–16 的「一帧一行」，新增 `rewrite` / `speak` 两类：

```
start        转写文本、风格、模型、字数上限
answer_delta 口语化改写的流式增量（前端边收边显示）
rewrite      改写完成：字数 + 残留 Markdown 计数（确定性）        ← 阶段 17 新增
speak        朗读稿 + 对照表 terms + termCheck 核对结果 + 时长估算 ← 阶段 17 新增
finish       全部结果 + 耗时
error        失败原因
```

**① 口语化改写**（流式）——system 提示词的关键在于把「念得顺」写成**硬性要求**：

```python
VOICE_SYSTEM = (
    "你是一个语音助手的「口语化改写」模块。……必须「念得顺、听得懂」。\n"
    "硬性要求：\n"
    "1. **不要任何 Markdown**：不要井号标题、不要减号或星号列表、不要加粗、"
    "不要反引号代码、不要链接、不要表格、不要 emoji；\n"
    "2. **用短句**：一句话尽量不超过 25 个字，用句号断句，方便朗读时换气；\n"
    "3. **不要括号注释**，也不要「1. 2. 3.」这种编号（要分点就说「第一…第二…」）；\n"
    …
)
```

三种风格共用同一套硬性约束，只在最后一句分岔：

| style | system 里追加的一句 |
|---|---|
| `brief` | 简洁作答：只讲最关键的结论 |
| `explain` | 展开讲解：先给结论，再补一到两个必要的理由 |
| `step` | 分步口述：按「第一步…第二步…」讲清做法 |

**② 朗读稿规范化**（JSON）——提示词把常见符号逐类列出，并要求**同时**返回对照表：

```python
TN_SYSTEM = (
    "……请把所有**符号化的写法**改写成**读出来的样子**：\n"
    "1. 日期：2026-09-21 → 二零二六年九月二十一日；\n"
    "2. 金额：¥2,158.50 → 两千一百五十八元五角；\n"
    "3. 数字：0.85 → 零点八五；3.5% → 百分之三点五；\n"
    "4. 缩写与型号：USB-C → U S B C；AI → A I；RAG → R A G；\n"
    "……另外，把所有做过改写的项**逐条**列进 terms。"
)
```

⚠️ 这里有一条**必须写进代码的降级策略**：规范化失败时**绝不能把内容弄丢**——

```python
def _normalize(client, answer, model, temperature):
    plan, _ = _json_call(client, messages, model, temperature, SpeakPlan, TN_HINT)
    if plan is None or not plan.speak.strip():
        return answer, []          # ← 保守降级：退回口语稿原文，照常能念
    return plan.speak.strip(), [...]
```

**③ 确定性体检**：`markdown_left()` + `spoken_profile()` + `audit_terms()`（见 §3.3），全部零成本。

### 4.2 端点 `main.py`：400 / 502，以及「先校验再开流」

```python
@app.post("/api/voice/run",    response_model=VoiceResponse)   # 非流式
@app.post("/api/voice/stream")                                 # 流式（前端用这个）
```

错误语义与阶段 16 一致：`voice.VoiceInputError`（转写文本空/超长）→ **400**（是**你**的问题），
其余 → **502**（是**上游**的问题）。流式端点同样**先校验、再开流**，否则错误只能以迟到的帧出现：

```python
try:
    voice._check_transcript(req.transcript)     # 先校验
except voice.VoiceInputError as e:
    raise HTTPException(status_code=400, detail=str(e)) from e
# 校验通过，才创建 StreamingResponse
```

⚠️ 还有一处**本阶段特意改掉**的写法。生成器里如果直接把异常抛出去，只会让流**断掉**——前端连半截结果都看不到。所以两个 LLM 阶段各自兜住异常，发一帧 `error` **再照常发 `finish`**（带着已有的部分结果）：

```python
try:
    for piece in client.stream(...):
        answer += piece
        yield {"type": "answer_delta", "text": piece}
except Exception as e:
    failure = f"口语化改写失败：{e}"      # 不抛穿；finish 仍会发出
```

于是 `VoiceResponse` 的 `error` 字段可以和部分结果**同时存在**——这让 `error` 从「摆设字段」变成了有意义的信号。

### 4.3 前端：拾音台是签名元素，且 ASR/TTS 都在浏览器

`useVoice.ts` 把 SSE 帧还原成：**口语稿（流式）**、**朗读稿**、**对照表 + 核对**、**体检数字**，
同时封装了两套 Web Speech API：

```ts
// ASR：注意 Chrome/Edge 至今仍以 webkit 前缀挂载，两个都要探
function pickRecognitionCtor() {
  if (typeof SpeechRecognition !== 'undefined') return SpeechRecognition
  if (typeof webkitSpeechRecognition !== 'undefined') return webkitSpeechRecognition
  return null
}

// TTS：规范化一到手就朗读 —— 这是"流式"在本阶段的真实收益
case 'speak':
  speak.value = p.speak ?? ''
  if (autoSpeak.value) speakOut(speak.value)
```

**为什么要自己写 `src/speech.d.ts`？** 因为 TypeScript 5.9.3 的 `lib.dom.d.ts` 里：

| | 状态 |
|---|---|
| `SpeechSynthesis` / `SpeechSynthesisUtterance` / `SpeechSynthesisVoice` | ✅ 有（TTS 侧不用补） |
| `SpeechRecognitionResult` / `...ResultList` / `...Alternative` | ✅ 有（结果类型不用补） |
| `SpeechRecognition` **本体** | ❌ **没有** |
| `SpeechRecognitionEvent` / `SpeechRecognitionErrorEvent` | ❌ **没有** |
| `webkitSpeechRecognition` | ❌ **没有** |

标准只把 Web Speech API 的**结果类型**收进了标准库，没把**识别器本体**收进去。于是 `new SpeechRecognition()`
直接 `Cannot find name`。**如实补上缺的那几块即可，不要重复声明已有的**（否则报重复标识符）。

`VoiceConsole.vue` 的四块：

1. **拾音台（签名元素）**：圆形麦克风按钮 + 9 根波形条（聆听时跳动，静止时是一条线，状态一眼可辨）+ 实时**临时转写**预览（`interimResults`）；
2. **风格分段控件**：`简洁` / `展开` / `分步`，蔚蓝高亮——本阶段的记忆点；
3. **结果区**：① 流式口语稿（带 Markdown 残留徽章）→ ② 朗读稿（带播放/暂停/语速/音色控制）→ ③ 规范化对照表（带 `termCheck` 核对徽章）；
4. **体检条**：口语稿字数 / Markdown 残留 / 朗读有效字 / 估算朗读时长，另加四格耗时分解。

> 视觉区分：阶段 13 青绿（决策链路）、14 琥珀（搜索框）、15 紫（研究大纲）、16 品红（图画布）、
> **17 蔚蓝（拾音台）**。同一套设计系统，五种记忆点。


**`brief` 的朗读稿（原样，差异处加粗）**：单号变成 **`B X 二零二六 零九一七`**，其余不变。

**`step` 的口语稿（原样）**：

```
差旅报销分三步走。第一步，填报销单，写清出差事由和起止日期。第二步，把发票和行程单贴好，附在单子后面。第三步，部门主管签字，再交财务审核打款。你这张单子九月二十一号已交。单号是 BX 二〇二六 〇九一七。金额两千一百五十八块五。想查进度，报单号问财务就行。
```

观察五点：

1. **「无 Markdown」这条硬约束在真实输出上成立了**：两次 `markdownLeft` 都是 **0**，
   而且改写稿确实是短句、句号断句、分点用「第一步…第二步…」而不是 `1. 2. 3.`。
   ⭐ 这印证了 §3.3 的判断——**一条正则就能替模型把关**，不需要再花一次调用去「检查格式」。
2. **风格差异是真实生效的**：`brief` 给四步概述 + 一句进度判断（117 字）；
   `step` 给「第一步/第二步/第三步」的口述流程（128 字）。同一个 `VOICE_SYSTEM`，只在最后一句分岔。
3. **规范化是整条链路里最贵的一步**：`brief` 9813 ms vs 改写 2088 ms（**4.7×**）；
   `step` 33365 ms vs 改写 845 ms（**39.5×**）。原因很具体——阶段 ② 是**非流式 JSON 调用**：
   它必须一次性产出「整篇规范化文本 + 结构化对照表」，既没有流式的逐字反馈，方差也明显更大
   （两段长度相近的文本，耗时差了 3.4 倍）。**这是需要留意的工程成本。**
4. ⭐ **两个阶段的职责会「串味」，而对照表只记录自己那一份**——这是本次实测最有价值的发现：
   `step` 那次，**改写阶段自己**就把 `2026-09-17` 写成了汉字（`二〇二六 〇九一七`），
   于是规范化阶段「无事可做」，`terms` 里只剩 `BX → B X`。
   只读对照表的人会得出错误结论：「数字没被改过」。**`terms` 是自述，不是 diff。**
   → 这正是我们补上 `termCheck` 的原因；用同一套判据复算两次真实结果，均为 **1/1 通过**，
   即**这次没有误导**，但**机制上它本来可以误导**——所以要把它变成可核对的。
5. **规范化的写法并不统一**：两次分别产出了 `零九一七` 与 `〇九一七`（`零` U+96F6 vs `〇` U+3007），
   连字符 `-` 也被换成了空格。对 TTS 来说都可以念，但这说明**规范化是「模型驱动」而非「规则驱动」**——
   想要完全一致，就得像阶段 04 那样上加**确定性规则表**兜底。

> ⚠️ 以上数字与文本全部来自本机实跑（真实 DeepSeek 调用），**没有伪造任何测量数据**。
> 你的环境耗时会有差异（阶段 ② 的方差尤其明显），但结构（先改写 → 再规范化 → 体检/核对）应一致。

## 6. 小结

- **先想清楚边界，再写代码**：一个平台事实（`/audio/*` 全 404）就唯一定下了整个架构——
  ASR/TTS 留浏览器，服务端只做文本侧。**「能用平台能力解决的事就别自己造。」**
- **「能读出来」≠「读得好」**：Markdown 标记和符号写法是两件必然发生的事故，各有对应解法
  （前者靠提示词硬约束，后者靠一次文本规范化）。
- **把主观要求变成可断言的数字**：「念得顺」不需要模型判定——一条正则数出 Markdown 残留，
  一个公式估算朗读时长。这是「能算的别问模型」的又一次体现。
- ⭐ **模型自述 ≠ 可核对**：`terms` 只记录它自己改了哪些，会漏报；一句 `in` 判断就能把它降级成可核对。
  这条暗线贯穿 14（`grounded`）→ 15（`faithful`）→ **17（`termCheck`）**。
- **降级策略要写进代码**：规范化失败退回口语稿原文（内容不丢）；生成器里不抛穿异常（部分结果照常返回）。
- **错误语义**：输入非法 → 400，上游失败 → 502；流式端点先校验再开流。

## 7. 练习与验收

**练习 1（改造题）**：给规范化加一层**确定性规则兜底**——先用正则处理最有把握的几类
（`\d{4}-\d{2}-\d{2}` 日期、`¥\d[\d,]*\.\d{2}` 金额、`\d+%` 百分比），再把剩下的交给 LLM，
并在 `terms` 里标出哪些是**规则改的**、哪些是**模型改的**。
思考：为什么这样一来 `termCheck` 的通过率会明显上升？

**练习 2（思考题）**：现在 `autoSpeak` 是「规范化一到手就整段朗读」。若要真正做到**边说边念**，
可以按句切分流式口语稿、逐句送进 `SpeechSynthesisUtterance` 的队列。
但这样会绕过阶段 ②——**先念出去的内容是没有被规范化的**。
请分析这两条路线各自的取舍（提示：延迟 vs 正确性，以及「说错了能不能收回」）。

**练习 3（扩展题）**：把本阶段与阶段 16 拼起来，做一个**「看图说话」**页面：
用户拍一张图 → 阶段 16 抽出字段 → 阶段 17 把结果改写成口语并朗读。
注意链路顺序：**应该先 `extract` 还是先 `qa`？** 为什么「先结构化、再用一句人话念出来」
比「让模型看着图直接念」更可控？
